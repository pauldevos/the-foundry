Identity, authorization and governance for Apps

Databricks Apps combines an app identity with optional user authorization. Unity Catalog governs the data and AI plane; OAuth governs machine and human access; resources make the dependency graph explicit. Treat every app-to-service edge as a permission decision.

The five questionsLeast privilege + auditability
The design question is not “can the app call it?” but “whose authority is being exercised, over which resource, for how long, and how is that decision audited?”

Default postureApp authorization is simplest for a controlled internal service. Use user authorization/OBO only when the user’s own UC permissions must be enforced at query/tool time. Never assume an app SP automatically inherits the caller’s permissions.
Choose the model
ScenarioModel
Shared public-ish internal dashboard with one curated datasetApp identity + app resource permissions; users only need app access.
Analyst sees only their region/tenantUser authorization/OBO + UC row filters/column masks; test deny paths.
Agent calls a function that mutates recordsSeparate write-capable resource, explicit scope, confirmation UX, immutable audit/event record.
CI deploys to prodGitHub OIDC → deployment SP; protected environment and CAN MANAGE only where needed.
External web app calls an App APIOAuth audience-scoped token, CAN USE, API route under /api/; do not expose workspace PATs.
Threat model firstModel prompt injection, confused deputy, over-broad app resources, data exfiltration through citations, token leakage in logs, replay, and a user asking an agent to use a tool they cannot use directly.
GUI build
  1. Workspace → Apps → create/edit app; set app permissions for viewers, users and managers.
  2. Add each Databricks resource by type and stable key; grant the app service principal the minimum permission (for example, warehouse CAN_USE).
  3. Enable user authorization only after the workspace admin enables the preview/feature; add the smallest scopes and test consent/revocation behavior.
  4. In Unity Catalog, grant the app SP (or underlying run-as identity) only the required catalog/schema/table/volume/function privileges.
  5. Configure secrets through the supported secret/resource mechanism; ensure values never appear in source, bundle logs or traces.
  6. Review audit logs, lineage, query history and app telemetry for a successful and a denied request.
Evidence required in a design reviewPermission matrix, token flow diagram, resource-to-scope mapping, row-filter test cases, secret rotation owner, audit destination, and emergency disable/revoke procedure.

Limits, alternatives, cost
ConcernTradeoff / mitigation
OBO/user auth previewAvailability and consent behavior can change. Gate it behind a feature flag and maintain an app-identity fallback only if that fallback is safe.
SP sprawlEvery app has a dedicated SP; inventory owners, rotate automation credentials, and avoid shared identities that erase audit boundaries.
SecretsUse Databricks secret/resource injection or an approved external manager. Redact logs and prompts; rotate on a schedule.
UC enforcementGovernance only works if all access paths use UC-governed resources. Direct external storage/API credentials can bypass the intended boundary.
NetworkPrivate connectivity, egress controls, customer-managed keys and compliance profiles are enterprise design inputs; Free Edition cannot validate them.
CostAudit, telemetry, endpoint calls and app compute cost money. Retain high-value traces, sample low-risk logs, and budget model/tool calls.
