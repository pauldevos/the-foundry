L0 — Source & IngestionParsing Layer
Extract clean text (and optionally tables, images) from raw documents before any splitting or embedding. Parser quality is the biggest RAG quality lever — garbage in, garbage out.
Typical Ingestion Pipeline
  1. Detect document type: PDF (text vs scanned), DOCX, HTML, CSV
  2. Choose parser based on layout complexity (see Tool Selection tab)
  3. Extract text; optionally extract tables as Markdown or structured objects
  4. Detect and flag scanned pages — route to OCR pipeline if needed
  5. Normalize whitespace, remove headers/footers, deduplicate boilerplate
  6. Attach source metadata: filename, page number, section title, last_modified
  7. Store parsed output in a staging store (UC Volume, S3) before chunking
Python · PyMuPDF fast text extraction
import fitz  # PyMuPDF

doc = fitz.open("drug_sop.pdf")
pages = []
for i, page in enumerate(doc):
    text = page.get_text("text")
    if not text.strip():  # scanned page — no text layer
        text = run_ocr(page)  # route to Tesseract / Azure DI
    pages.append({"page": i, "text": text, "source": "drug_sop.pdf"})

  • How do you handle PDFs with mixed text and tables?
    Two options: (1) Unstructured with strategy="hi_res" — uses a layout detection model to identify table regions, then extracts them as Markdown rows. (2) Azure Document Intelligence — highest accuracy for forms and complex tables, worth the API cost for compliance docs. Avoid PyMuPDF alone; it serializes table cells in reading order which destroys table semantics.
  • What's your OCR strategy for scanned documents?
    Detect blank text pages post-extraction (len(text.strip()) == 0 after PyMuPDF). Route those pages to: Azure Document Intelligence for highest accuracy (handles mixed printed + handwritten), or Tesseract via Unstructured strategy="ocr_only" for open-source. Cache OCR output — it's expensive to re-run. Store OCR confidence score as metadata for quality filtering.
  • How do you handle document updates without full re-ingestion?
    Delta ingestion: track last_modified timestamp per document. On scheduled runs, only re-parse docs where last_modified > last_indexed. Soft-delete old vectors by doc_id in the vector store, re-embed new chunks, insert fresh. This requires storing doc_id and chunk_index as vector metadata from the start.
L1 — Chunking StrategySplitting Layer
Split parsed text into retrieval units. Chunk size controls the precision/context tradeoff — too small loses context, too large retrieves noise. Strategy choice affects both build time and retrieval quality.
Python · Recursive character splitter (LangChain default)
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=64,   # ~12.5% overlap
    separators=["\n\n", "\n", ". ", " ", ""],
)
chunks = splitter.split_text(document_text)
# Attaches source metadata per chunk manually:
docs = [
    {"text": c, "source": filename, "chunk_id": i}
    for i, c in enumerate(chunks)
]
Python · Hierarchical parent-doc retriever (best for tables)
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore

# Child chunks (small, what gets embedded)
child_splitter = RecursiveCharacterTextSplitter(chunk_size=256)
# Parent chunks (large, what gets returned to LLM)

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=InMemoryStore(),
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,

# Retrieves parent (full context) when child chunk matches
ParameterValues / Notes
chunk_size256 (precision), 512 (sweet spot default), 1024 (context-rich); measure with Hit Rate + MRR
chunk_overlap10–20% of chunk_size; prevents boundary misses; 64 tokens for 512-token chunks
separatorsRecursive: try \n\n → \n → ". " → " " → ""; respects document structure
length_functionlen (characters) or tokenizer.encode (tokens); token-based aligns with embedding model limits
child_chunk_sizeHierarchical: 128–256 for child (embedded), 512–1024 for parent (returned)
Chunk Size vs Retrieval QualitySmaller chunks = higher precision (exact match), lower recall (context truncated). Larger chunks = more context per result, but may retrieve irrelevant surrounding text. Always test at 256/512/1024 with your actual eval set using Hit Rate and MRR before committing.
Semantic Chunking CostSemantic chunking (embedding-based boundary detection via sentence-transformers) adds 3–5x build time vs fixed-size. Only worth it for documents where paragraph breaks are meaningful (research papers, SOPs). Not for tabular data or forms.

  • How do you choose chunk size?
    Empirically: build three indexes at chunk_size 256, 512, and 1024. Evaluate each with a test question set using Hit Rate (is the answer in top-k?) and MRR (mean reciprocal rank). The chunk size with the best tradeoff on your corpus wins. As a starting point: 512 with 64-token overlap is the most common default for mixed prose/technical content.
  • What's the best chunking strategy for documents with tables?
    Hierarchical parent-document retriever. Index small child chunks (256 tokens) for precise matching, but return the full parent chunk (1024 tokens) to the LLM so table context is preserved. Alternatively, extract tables separately as their own document units with structured Markdown formatting, embedding each table as a single chunk regardless of size.
  • Why does chunk overlap matter?
    Without overlap, a sentence split across a chunk boundary loses meaning in both chunks. Overlap of 10–20% ensures that boundary-spanning content appears in at least one chunk fully. The cost is ~20% more vectors in your index. The benefit is significantly fewer retrieval misses on boundary-sensitive queries (dates, names, numerical facts that span sentences).
L2 — EmbeddingDense Vector Layer
Convert text chunks into fixed-dimension dense vectors. Model choice affects both retrieval quality and operational cost. Embeddings must be regenerated if the model changes — version them carefully.
Python · OpenAI embedding with batching
from openai import OpenAI
import numpy as np

client = OpenAI()

def embed_batch(texts: list[str], model="text-embedding-3-small"):
    resp = client.embeddings.create(input=texts, model=model)
    vecs = [r.embedding for r in resp.data]
    # L2-normalize for cosine similarity
    arr = np.array(vecs)
    return arr / np.linalg.norm(arr, axis=1, keepdims=True)

# Batch in chunks of 512 to stay within API limits
all_vecs = []
for i in range(0, len(texts), 512):
    all_vecs.extend(embed_batch(texts[i:i+512]))

    batch_size=64,

  • How do you keep embeddings fresh when documents change?
    Delta indexing: track doc_id + last_modified. On update: (1) soft-delete old vectors by doc_id (most stores support filter-based delete), (2) re-parse the changed doc, (3) re-chunk and re-embed, (4) insert new vectors with updated metadata. For continuous pipelines, hook into document change events (S3 notifications, SharePoint webhooks) to trigger re-embedding. Never full re-index unless forced — it's expensive and causes downtime.
  • Should I use asymmetric embedding (separate query/doc models)?
    Yes for production. Cohere and BGE support input_type="search_query" vs "search_document" — the model produces different embeddings optimized for each role. Query embeddings are shorter and intent-focused; document embeddings are content-rich. Using the same embedding for both is fine for prototyping but leaves performance on the table. Always use the query-type embedding at retrieval time.
  • Local embedding model vs API — when do you choose local?
    Local (BGE, nomic): no API cost at inference, data never leaves your network (critical for regulated industries), consistent latency without API quota limits. API (OpenAI, Cohere): state-of-the-art quality, no infra to maintain, versioned by provider. For high-volume ingestion (millions of docs), local GPU embedding is 10-100x cheaper. For compliance-sensitive data (PHI, trade secrets), local is often mandatory.

  • HNSW vs IVF — when do you use each?
    HNSW (Hierarchical Navigable Small World): best recall for under ~50M vectors, graph-based traversal, RAM-heavy (full graph must fit in memory), slower inserts but fast queries. IVF (Inverted File): clusters vectors into Voronoi cells, searches only nprobe clusters — disk-friendly, scales to hundreds of millions of vectors, but recall depends heavily on nprobe tuning. Rule of thumb: HNSW for typical enterprise RAG (thousands to low millions of chunks); IVF for massive corpora.
  • How do you handle multi-tenancy in a vector store?
    Three patterns: (1) Namespace/collection per tenant — full isolation, higher resource cost; (2) Metadata-filtered single collection — tenant_id as payload field, filter on every query — simpler ops but weaker isolation; (3) Separate indexes per tier (admin, user, read-only) — hybrid approach. For regulated data (PHI, customer PII): namespace-per-tenant is safest; the small performance cost is worth the isolation guarantee. Add tenant_id to every metadata payload from day one even if starting with a single tenant.
L4 — RetrievalSearch & Reranking Layer
Convert a user query into a ranked list of relevant chunks. Hybrid search (dense + sparse) outperforms either alone. Reranking adds a cross-encoder pass to boost precision before generation.
Python · Hybrid search + RRF fusion + Cohere reranking
import cohere
from rank_bm25 import BM25Okapi

co = cohere.Client("COHERE_API_KEY")

# 1. Dense retrieval (ANN from vector store)
dense_results = vectorstore.search(query_vec, k=20)

# 2. Sparse retrieval (BM25 keyword)
bm25 = BM25Okapi(tokenized_corpus)
sparse_results = bm25.get_top_n(query.split(), corpus, n=20)

# 3. RRF fusion: score = Σ 1/(k + rank_i), k=60
def rrf(results_lists, k=60):
    scores = {}
    for results in results_lists:
        for rank, doc in enumerate(results):
            scores[doc.id] = scores.get(doc.id, 0) + 1 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)

fused = rrf([dense_results, sparse_results])[:20]

# 4. Rerank top-20 to top-4 with cross-encoder
reranked = co.rerank(
    model="rerank-english-v3.0",
    query=query,
    documents=[d.text for d in fused],
    top_n=4,
)
ParameterValues / Notes

top_k (retrieval)20–50 candidates from vector store before reranking
top_n (rerank)3–5 final chunks passed to LLM; balance context vs noise
alpha (hybrid weight)Some stores expose α: 0=pure BM25, 1=pure dense; 0.7 dense + 0.3 sparse is a common start
score_thresholdFilter results below min relevance score (0.3–0.5); triggers "I don't know" fallback
MMR lambdaMaximal Marginal Relevance: 0=max diversity, 1=max relevance; 0.5–0.7 typical
Reranking ROIRetrieve k=20 → rerank to k=4 with Cohere Rerank or a cross-encoder. Adds 100–300ms latency but improves precision 15–25% on benchmarks. The reranker reads query + document together (cross-encoder), not independently — it's a fundamentally better relevance signal than bi-encoder similarity.

  • What is Reciprocal Rank Fusion and why does k=60?
    RRF merges multiple ranked lists using score = Σ 1/(k + rank_i) for each list. A document appearing at rank 1 in both lists scores highest. k=60 is the default constant that smooths differences between high-ranked results — empirically found to work well across many datasets in the original RRF paper. It's rank-based (not score-based), so it doesn't require calibrating similarity scales between BM25 and cosine scores.
  • When would you use dense-only retrieval vs hybrid?
    Dense-only: purely conceptual queries over uniform prose (e.g. "what does this policy say about…"). Hybrid is better almost universally in production because real user queries mix concepts with exact terms (drug names, order IDs, product codes). If your corpus contains any identifiers, codes, or proper nouns, hybrid will outperform dense-only. The cost of adding BM25 is low; the precision gain is consistent.
  • What's your reranking strategy?
    Retrieve top-20 candidates from the vector store (hybrid). Pass to Cohere Rerank v3 or a local ms-marco cross-encoder. Return top-4 to the LLM. Apply a score threshold (0.3–0.5 depending on the task) — if top result is below threshold, don't generate; return a fallback ("I couldn't find relevant information"). Reranking adds 100–300ms; acceptable for most use cases, not for sub-100ms latency SLAs.
L5 — Generation & GuardrailsLLM Output Layer
Generate a grounded answer from retrieved context using an LLM. Prompt structure, temperature, and faithfulness checks determine whether the output is trustworthy or hallucinatory.
Python · Minimal RAG generation prompt
from openai import OpenAI

client = OpenAI()

SYSTEM = """You are a document assistant. Answer ONLY from the provided context.
If the context does not contain the answer, say: 'I don't have that information.'
Always cite the source document name and page number inline, e.g. [drug_sop.pdf p.4]."""

def generate(query: str, chunks: list[dict]) -> str:
    context = "\n\n".join(
        f"[{c['source']} p.{c['page']}]\n{c['text']}"
        for c in chunks
    )
    resp = client.chat.completions.create(
        model="gpt-4o",
        temperature=0,        # factual; no creativity
        max_tokens=512,
        messages=[
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {query}"}
        ]
    )
    return resp.choices[0].message.content

  • How do you prevent hallucinations in a RAG system?
    Four layers: (1) System prompt: "Answer ONLY from the provided context. If not present, say 'I don't have that information.'" (2) Retrieval score threshold: if max similarity < 0.4, skip generation entirely. (3) Citation format: require inline citations [source p.N] — forces the model to stay grounded. (4) Offline eval: RAGAS faithfulness metric on a test set catches prompt regressions. No single mechanism is sufficient; the full stack is necessary for production.
  • What RAGAS metrics matter most and why?
    Faithfulness: are all answer claims supported by retrieved context? (prevents hallucination — most critical). Context Recall: was all relevant ground-truth info in the retrieved context? (retrieval quality signal). Answer Relevancy: does the answer address the question? (prompt quality signal). Context Precision: are retrieved docs actually relevant? (retrieval noise signal). Run all four; faithfulness and context recall together tell you whether the problem is retrieval or generation.
  • How do you structure the prompt for RAG?
    System message = (1) role/persona, (2) grounding instruction ("answer only from context"), (3) citation format instruction, (4) fallback instruction ("say I don't know if absent"). User message = formatted context chunks with source labels + the question. Never put the grounding instruction only in the user message — system prompt has stronger instruction weight. Temperature = 0 for factual retrieval tasks. Set max_tokens based on expected answer length, not the model max.
System DesignEnd-to-End RAG
How the layers connect, how to evaluate the full pipeline, when NOT to use RAG, and how to monitor in production. The interview expects you to reason across all layers simultaneously.
End-to-End Pipeline Flow
  1. Ingest: Parse documents (PyMuPDF / Unstructured / Azure DI) → normalize text → attach metadata
  2. Chunk: Recursive character splitter (512 tokens, 64 overlap) or hierarchical for structured docs
  3. Embed: Batch embed with text-embedding-3-small or bge-m3; L2-normalize; store model version
  4. Index: Upsert to vector store (Qdrant/Pinecone/AI Search) with metadata payload
  5. Retrieve: Hybrid search (dense + BM25) → RRF fusion → retrieve top-20
  6. Rerank: Cohere Rerank or cross-encoder → top-4 chunks; apply score threshold
  7. Generate: Grounded system prompt → LLM (GPT-4o / Claude) at temperature=0 → response with citations
  8. Eval: RAGAS offline + user feedback online → tune retrieval or prompt based on failing metric
Eval-Driven Iteration LoopRun RAGAS on a test set after every change. Low faithfulness → fix prompt or retrieval threshold. Low context_recall → fix chunking or retrieval k. Low answer_relevancy → fix prompt. Low context_precision → add metadata filtering. Never tune blindly — always trace the failing metric to the responsible layer.
Monitoring in Production
  • Track latency per stage: ingestion, embedding, retrieval, rerank, generation
  • Log retrieval score distribution — degradation signals embedding drift or index staleness
  • Collect thumbs-up/down signals for online eval; correlate with RAGAS offline metrics
  • Alert on faithfulness drops (<0.8) and retrieval score floor drops (>20% below threshold)

When NOT to Use RAG
  • Pure retrieval: User just wants docs returned — no LLM generation needed
  • Real-time data: RAG is batch-indexed; use structured DB or streaming query instead
  • Closed-domain with stable knowledge: Fine-tuned model may outperform RAG if facts are static and <512 tokens total
  • Sub-50ms latency SLA: Reranking + LLM generation adds 500ms–2s; use search-only for latency-critical paths

  • RAG vs fine-tuning — how do you decide?
    RAG when: (1) the knowledge base changes frequently — you just re-index, no retraining; (2) the knowledge volume is large — can't fit everything into model weights; (3) source citations are required for compliance or auditability; (4) you need the model to reason over documents it wasn't trained on. Fine-tune when: (1) you need a specific output style or format the base model doesn't have; (2) the knowledge is small, static, and fits in the fine-tuning dataset; (3) you're optimizing for query latency and cost at massive scale. In most enterprise RAG scenarios, both are used: RAG for dynamic knowledge retrieval, fine-tuning for output format/style.
  • Walk me through how you'd debug a RAG system with low answer quality.
    Start with RAGAS to diagnose which layer is failing. (1) Low context_recall → retrieval is missing relevant docs: check chunk size (too small?), retrieval k (too low?), embedding model fit, metadata filtering too restrictive. (2) Low faithfulness → LLM is hallucinating: tighten system prompt grounding instruction, lower temperature to 0, add score threshold fallback. (3) Low context_precision → too much noise in retrieved chunks: add metadata filters, lower k, add reranking. (4) Low answer_relevancy → generation is off-topic: improve system prompt specificity, check query understanding. Always isolate retrieval from generation — test retrieval quality independently with Hit Rate before touching the LLM.
  • How do you scale a RAG pipeline from prototype to production?
    Five shifts: (1) Ingestion: from sync to async batch pipeline with delta re-indexing, not full re-index on every update. (2) Embedding: from single API calls to batched async requests or local GPU inference for cost. (3) Vector store: from ChromaDB/local to managed Qdrant/Pinecone/AI Search with HA. (4) Retrieval: add reranking, hybrid search, metadata filtering — prototype with dense-only is fine. (5) Eval: move from manual inspection to RAGAS on a curated test set in CI; add online feedback loop (thumbs up/down). Also: pin embedding model versions, add monitoring on retrieval score distributions, implement circuit breakers for LLM timeouts.
