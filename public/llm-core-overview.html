Context WindowsToken limits · Truncation · Long context models
The context window is the LLM's working memory — it sees nothing outside it. Every design decision in RAG, agents, and multi-turn conversations is constrained by context window limits and the "lost in the middle" effect.
ModelContext windowPractical limitNote
claude-sonnet-4-5200K tokens~150K usableStrong long-context performance; 8K max output
gpt-4o128K tokens~100K usablePerformance degrades noticeably past 64K
Llama-3.1-70B128K tokens~64K usableOpen weights; self-hosted; quality drops at long context
DBRX32K tokens~24K usableDatabricks-native; efficient for structured tasks
gemini-1.5-pro1M tokens~500K usableLargest available; cost and latency significant at long context
War Story — Silent Truncation Loaded an entire oil and gas pipeline safety specification (340 pages, ~180K tokens) into a 128K context model. No error — the API accepted the request and returned a confident answer. The answer was wrong. The model had silently truncated the input; the critical safety clause was in the truncated section. The model hallucinated a plausible-sounding regulation from parametric memory. Added a token count check before every API call: if input_tokens > 0.85 × context_limit, route to chunked RAG instead of full-document context.
  • Count tokens explicitly — use tiktoken (OpenAI) or the Anthropic token counting API before sending; don't trust that the API will error on overflow
  • Lost in the middle — models attend most strongly to the beginning and end of long contexts; content in the middle gets less weight; put the most critical context first
  • Long context ≠ long memory — larger windows allow more input but don't improve reasoning over that input proportionally; RAG is still better for selective retrieval over large corpora
Python · Token counting + truncation guard before API call
import anthropic
from anthropic import Anthropic

client = Anthropic()
MODEL = "claude-sonnet-4-5"
CONTEXT_LIMIT = 200_000
SAFETY_MARGIN = 0.85  # use at most 85% of context

def count_tokens(messages: list[dict], system: str = "") -> int:
    response = client.messages.count_tokens(
        model=MODEL,
        system=system,
        messages=messages,
    )
    return response.input_tokens

def safe_invoke(messages, system="", fallback_fn=None):
    token_count = count_tokens(messages, system)
    max_allowed = int(CONTEXT_LIMIT * SAFETY_MARGIN)

    if token_count > max_allowed:
        print(f"Context too large: {token_count} tokens. Routing to RAG fallback.")
        if fallback_fn:
            return fallback_fn(messages)
        raise ValueError(f"Input exceeds safe context limit: {token_count}/{max_allowed}")

    return client.messages.create(
        model=MODEL, system=system, messages=messages, max_tokens=2048
    )
  • When would you use a long-context model instead of RAG?
    Long-context shines for tasks where the model needs to reason across the FULL document simultaneously — not just retrieve a relevant section. For example: contract review where a clause on page 5 modifies definitions on page 2 and exceptions on page 40; legal analysis where cross-references matter; code review of a full codebase where understanding one function requires knowing another. RAG retrieves relevant fragments but loses the global structure. Long-context preserves it. The trade-offs: cost (200K tokens per query vs. 5K tokens in RAG), latency (proportional to context length), and the lost-in-the-middle problem. For selective lookup — "what does this policy say about X?" — RAG is better. For holistic reasoning — "are there any contradictions in this contract?" — long context wins.
Prompt EngineeringFew-shot · Chain-of-thought · System prompts · Sensitivity
Prompt engineering is not a soft skill — it's the primary interface to model behavior. Small wording changes cause large behavior changes. The goal is prompts that are explicit, testable, and version-controlled.
TechniqueWhen to usePitfall
Zero-shotSimple, well-defined tasks the model handles without examplesUnderspecified — model interprets ambiguity however it wants
Few-shotFormat consistency; domain-specific tone; edge cases you want handled a certain wayModel pattern-matches too hard on examples; misses out-of-distribution inputs
Chain-of-thought (CoT)"Let's think step by step" or explicit reasoning steps for math, logic, multi-stepAdds tokens; model can reason correctly but still give wrong final answer
System promptPersistent behavior rules: role, output format, refusal behavior, citation requirementsModel doesn't always follow — instructions are probabilistic, not hard constraints
XML structureSeparating context/instructions/query clearly for Claude; prevents bleed between sectionsOther models may not respond as well to XML framing
Prompt Sensitivity War Story Changed "Answer the question" to "Answer the question concisely" in a production system prompt. Faithfulness on the eval set dropped from 0.83 to 0.71. The model was abbreviating answers by omitting supporting details — technically more concise, but less faithful. One word change, 12-point regression. Now every system prompt change runs through the full eval suite before shipping.

  • How do you handle prompt sensitivity in production?
    Three practices. First, version control: every system prompt lives in a config file with a version string, checked into git. No ad-hoc prompt edits in production. Second, eval gate: any prompt change runs the full RAGAS eval suite before merging — I've seen a one-word change cause a 12-point regression. Third, A/B testing for significant changes: route 10% of traffic to the new prompt for 48 hours, compare online faithfulness and user satisfaction scores, then promote or revert. The key insight is that prompts are code: they have bugs, they need tests, and they need deployment discipline.
  • When do few-shot examples hurt more than they help?
    When the examples are too narrow and the model pattern-matches on format rather than reasoning. I saw this with a drug interaction checker — few-shot examples all had confident "yes/no" answers, so the model started giving confident answers to genuinely ambiguous interactions instead of flagging uncertainty. The examples were teaching the wrong behavior. Fix: add examples that demonstrate the uncertainty case ("This interaction has limited clinical data — consult a pharmacist"). Also: when input distribution shifts and examples no longer represent real queries. Review your few-shot examples quarterly, not just at launch.
Structured OutputPydantic · JSON mode · Tool use · Parser failures
Getting consistent structured output from LLMs — JSON, typed objects, validated schemas — is harder than it looks. The model is a text generator; structure is imposed on top. Every approach has failure modes.
MethodReliabilityFailure modeWhen to use
Prompt + parse JSONLowModel adds markdown, commentary, trailing comma, wrong typesNever in production
JSON modeMediumValid JSON but wrong schema; missing required fields; wrong enum valuesPrototyping; simple schemas
Tool/function callingHighModel calls wrong tool; skips required args; argument type mismatchProduction; structured extraction
with_structured_output (Pydantic)HighValidation errors on complex nested schemas; enum fields with many optionsProduction; typed Python objects
Instructor libraryVery HighAdds retry overhead; slower on retriesComplex schemas needing auto-retry on validation failure
War Story — JSON Mode Silent Failure Used JSON mode to extract drug interaction severity (enum: "low", "medium", "high", "contraindicated"). Model returned valid JSON with "severity": "High" — capital H, not in the enum. The downstream parser did a case-sensitive match and silently classified "High" as unknown, defaulting to "low" severity. A contraindicated interaction was displayed as low severity. Switched to with_structured_output(Pydantic) with a Literal["low","medium","high","contraindicated"] field — Pydantic validates and rejects invalid values at parse time.
Python · Pydantic structured output with validation and retry
from pydantic import BaseModel, Field, field_validator
from typing import Literal
from langchain_anthropic import ChatAnthropic

class ClaimResolution(BaseModel):
    claim_id:   str
    status:     Literal["approved", "denied", "escalated", "pending_info"]
    confidence: float = Field(ge=0.0, le=1.0)
    reasoning:  str   = Field(min_length=20)
    amount_usd: float = Field(ge=0)

    @field_validator("reasoning")
    def reasoning_must_cite_evidence(cls, v):
        if "[Doc:" not in v and "[Source:" not in v:
            raise ValueError("Reasoning must cite a source document")
        return v

llm = ChatAnthropic(model="claude-sonnet-4-5")
# with_structured_output: model uses tool_use internally;
# Pydantic validates; raises ValidationError on schema mismatch
structured_llm = llm.with_structured_output(ClaimResolution, include_raw=False)

resolution: ClaimResolution = structured_llm.invoke(prompt)
  • JSON mode returned valid JSON but the schema was wrong. How do you prevent that?
    JSON mode only guarantees syntactically valid JSON — it doesn't validate against your schema. Three defenses: (1) Use with_structured_output(Pydantic) instead — it sends the schema to the model via function calling, which is schema-aware, not just syntax-aware. Pydantic then validates the parsed result. (2) If you must use JSON mode, add explicit schema description in the system prompt AND validate the output with a Pydantic model — catch the mismatch programmatically rather than silently passing wrong data downstream. (3) Use the Instructor library, which wraps any LLM with automatic retry on Pydantic ValidationError — it re-prompts the model with the validation error message and tries again up to N times.
Sampling & TemperatureTemperature · top-p · top-k · Determinism
Temperature controls randomness. But "set it to 0 for accuracy" is an oversimplification — temperature interacts with the task, the model, and what "correct" means. Understanding sampling matters for debugging non-deterministic failures.
ParameterEffectTypical rangeWhen to tune
temperatureScales logit distribution; 0 = deterministic (greedy); 1 = default; >1 = more random0–10 for structured extraction/code; 0.3–0.7 for Q&A; 0.7–1 for creative
top_p (nucleus)Sample from the smallest set of tokens whose cumulative probability ≥ p0.9–1.0Lower (0.7–0.9) to reduce rare token selection; rarely tuned
top_kRestrict sampling to the K most probable tokens50–100Rarely needed if temperature is set; Anthropic doesn't expose top_k
max_tokensHard cap on output length; model stops even mid-sentenceTask-dependentSet explicitly; never rely on default; too-low truncates answers
  • Temperature 0 is not truly deterministic — floating-point arithmetic on parallel GPUs introduces non-determinism even at temp=0; use seeds where available for reproducibility
  • High temperature + structured output = more failures — at temperature 0.8, the model is more likely to generate slightly wrong field names or out-of-enum values; use 0–0.3 for structured extraction
  • Debugging non-determinism — if a prompt works 90% of the time but fails 10%, temperature is often the culprit; lower it or add more explicit format instructions
Python · Temperature by task type + seed for reproducibility
from anthropic import Anthropic
client = Anthropic()

def call_model(messages, task_type: str, **kwargs):
    temp_map = {
        "extraction":  0.0,   # structured data extraction → deterministic
        "qa":          0.3,   # factual Q&A → low variation
        "summarize":   0.5,   # summarization → some flexibility
        "creative":    0.8,   # generation → more variety
    }
    temperature = temp_map.get(task_type, 0.3)

    return client.messages.create(
        model="claude-sonnet-4-5",
        messages=messages,
        temperature=temperature,
        max_tokens=kwargs.get("max_tokens", 1024),
    )

  • Why would you use temperature > 0 for a factual Q&A system?
    Two reasons. First: temperature 0 (greedy decoding) can get stuck in repetitive loops on some models — it always picks the single highest-probability token, which can create degenerate outputs on ambiguous prompts. A small temperature (0.1–0.3) introduces just enough variation to break loops while keeping output stable. Second: for Q&A where there are multiple valid correct phrasings, a tiny amount of temperature produces more natural, varied responses — users notice when every answer sounds like it came from the same template. In practice, for a benefits chatbot I'd use 0.2–0.3: low enough to be consistent and accurate, high enough to sound human and avoid loops.
Fine-tuning vs PromptingWhen to fine-tune · LoRA · Instruction tuning · Cost
Fine-tuning is often reached for too early. Prompting + RAG solves 80% of problems at 10% of the cost and time. Fine-tuning is warranted for specific, well-defined failure modes that prompting cannot fix.
Use fine-tuning whenUse prompting/RAG when
You have 1,000+ high-quality labeled examples of the exact behavior you wantYou don't have training data or it would take weeks to create
Prompting has hit a ceiling — you've tried CoT, few-shot, and the behavior still isn't reliableYou haven't tried few-shot, CoT, or structured output yet
Latency matters and you need a smaller model to match a larger model's quality on a narrow taskThe task is broad and generalization matters
Domain vocabulary or format is so specific it's hard to convey in a prompt (code style, medical terminology)The behavior can be demonstrated in 3-5 examples
You need to reduce hallucination on a very narrow, well-defined task with known correct answersKnowledge changes frequently — fine-tuning bakes in a snapshot
LoRA on Databricks Databricks Model Serving supports fine-tuning open-weight models (Llama, Mistral) with LoRA (Low-Rank Adaptation) via the Fine-Tuning API. LoRA fine-tunes a small number of adapter weights rather than the full model — 10-100× cheaper than full fine-tuning, comparable quality for most tasks. Output: a Delta-registered model artifact deployable to Model Serving.

  • How do you decide whether to fine-tune or improve the prompt?
    Run the experiment in that order — prompt first, fine-tune only if prompted. Concrete decision gate: if I have a specific, measurable failure (e.g., the model consistently formats drug dosages wrong, or uses lay terms instead of clinical terminology), I first try a few-shot example of the correct behavior. If 5 examples don't fix it, I try 20. If 20 examples in the prompt don't reliably fix it, I have evidence that the behavior requires parametric knowledge, not just in-context demonstration — and now I have my training data already (those 20 examples become the seed for a fine-tuning dataset). Fine-tuning also makes sense when the prompt is getting unwieldy — if you're spending 2K tokens on examples and instructions, a fine-tuned model can collapse that to a 200-token system prompt.
HallucinationWhy it happens · Detection · Mitigation · Grounding
Hallucination is not a bug — it's a feature of how language models work. They generate the most probable next token, not the most accurate one. Mitigation requires architecture decisions, not just prompting.
Hallucination typeExamplePrimary mitigation
IntrinsicAnswer contradicts the provided context directlyFaithfulness eval + citation requirement
ExtrinsicAnswer cannot be verified or contradicted by context — model adds new "facts"RAG grounding; close-book prompting
ParametricModel answers from training data instead of provided context (stale facts)"Answer only from the documents" + evidence requirement
Confident uncertaintyModel gives a definite answer to an unanswerable questionExplicit escape hatch in prompt; "I don't know" examples
  • Why it happens — LLMs are trained to predict the next token, not to flag uncertainty; the most fluent, confident-sounding token sequence is often reinforced during RLHF
  • Bigger models hallucinate differently — they hallucinate less on factual recall but more confidently when they do; smaller models hallucinate more but sometimes hedge ("I'm not sure")
  • Citations as grounding — requiring a citation for every claim forces the model to verify against context before generating; it can't cite what isn't there
  • Consistency checking — generate 3 answers at slightly different temperatures; if they disagree significantly, the model is uncertain; flag for human review
Python · Self-consistency check for high-stakes answers
import re
from langchain_anthropic import ChatAnthropic

llm = ChatAnthropic(model="claude-sonnet-4-5")

def consistent_answer(prompt: str, n: int = 3, agreement_threshold: float = 0.67) -> dict:
    """Generate N answers; return answer only if majority agree."""
    answers = []
    for temp in [0.0, 0.3, 0.5]:
        response = llm.invoke(prompt, config={"temperature": temp})
        answers.append(response.content.strip())

    # Simple agreement: check if dominant answer appears in majority
    from collections import Counter
    # Normalize: extract key facts (e.g., dollar amounts, yes/no)
    normalized = [extract_key_claim(a) for a in answers]
    most_common, count = Counter(normalized).most_common(1)[0]

    agreement = count / n
    if agreement >= agreement_threshold:
        return {"answer": answers[0], "confidence": agreement, "escalate": False}
    return  {"answer": None, "confidence": agreement, "escalate": True}
  • The model was confidently wrong on a drug interaction question. What did you do?
    Three things in response. Immediate: added that specific interaction to the eval set as a hard failure case. Added a rule to the system prompt: "For any drug interaction question, you MUST state the source document and section. If you cannot find the interaction in the provided formulary documents, say 'This interaction is not documented in our current formulary. Consult the prescribing pharmacist.' Never infer or extrapolate drug interactions." Medium-term: added a self-consistency check for drug interaction queries specifically — generate the answer at three temperatures, only auto-respond if 2 of 3 agree on the key claim (safe/unsafe/unknown). Any disagreement routes to human pharmacist review. The confidence was the dangerous part — the model had learned from RLHF to sound authoritative. The escape hatch instruction was necessary to override that.
