Parser Comparison + OCR Fallback
Python · Unstructured with hi_res + length-based OCR fallback
from unstructured.partition.pdf import partition_pdf
from pathlib import Path

def parse_pdf(path: str) -> list[dict]:
    # First pass: fast native extraction
    elements = partition_pdf(path, strategy="fast")
    text_len = sum(len(e.text) for e in elements if hasattr(e, "text"))

    if text_len < 500:
        # Likely scanned — fall back to OCR-based hi_res
        print(f"Low text yield ({text_len} chars), retrying with OCR: {path}")
        elements = partition_pdf(
            path,
            strategy="hi_res",
            infer_table_structure=True,
            languages=["eng"],
        )

    chunks = []
    for el in elements:
        if el.category == "Table":
            # Preserve tables as markdown — don't let them get chunked mid-row
            chunks.append({"text": el.metadata.text_as_html, "type": "table"})
        elif hasattr(el, "text") and len(el.text.strip()) > 30:
            chunks.append({"text": el.text, "type": el.category})
    return chunks
  • Your RAGAS scores were good in dev but fell apart in production. What happened?
    Classic parser mismatch. Dev used a clean, single-column PDF I'd prepared manually. Production ingested 40+ documents from different years — some scanned, some multi-column, one was a PowerPoint exported as PDF. The fast parser returned garbled text for all three cases. I added a parse quality check at ingest time: char count per page, table detection, and a short human spot-check on 5 random chunks. Anything below the threshold got flagged for manual review or routed to the hi_res OCR path. After that, context recall went from 0.61 to 0.83.
  • How do you handle documents that have tables? They always seem to break retrieval.
    Two strategies depending on the table type. If the table has a clear semantic header row (like a benefits comparison table), I serialize it to Markdown and store the whole table as a single chunk with a metadata tag type=table. This keeps row context intact. If the table is huge (like a drug formulary with 3,000 rows), I convert each row to a sentence: "Drug X has tier 2 coverage with a $40 copay and requires prior auth." That way each row is retrievable independently and the model sees natural language rather than a cell dump.
Chunking StrategyFixed-size · Semantic · Hierarchical · Overlap
How you split documents determines what the retriever can find. Too large: irrelevant content dilutes the answer. Too small: context is lost mid-thought. The right strategy depends on document structure, not a default token count.
StrategyHow it worksFails when
Fixed-sizeSplit every N tokens, optional overlap of K tokensSplits mid-sentence, mid-clause, mid-table row. Works only on narrative prose.
Recursive characterTry splitting on \n\n, then \n, then ". ", then " " — use the largest that fits under limitBetter than fixed-size but still arbitrary at paragraph boundaries
SemanticEmbed sentences, find cosine similarity drops → split at topic boundariesSlow, expensive. Boundary detection noisy on technical docs with dense jargon.
Hierarchical / parent-childIndex small child chunks for retrieval, but return the parent chunk to the modelParent chunks must be well-defined (section, page). Poorly structured docs have no clear parent.
Document-nativeUse document's own structure: headings, sections, pages as chunk boundariesBest strategy when it works. Requires rich metadata from the parser.
War Story Pattern — Policy Documents Used 512-token fixed-size chunks on an HR handbook. The chunk boundary landed in the middle of a sentence about FMLA eligibility: one chunk ended with "Employees are eligible for FMLA leave if they have worked at least" and the next started with "1,250 hours in the past 12 months." Queries about FMLA eligibility returned the first chunk — the model said the eligibility criteria were unclear. Switched to recursive splitting on section headers, overlap of 50 tokens. FMLA answers became accurate.
  • Overlap is a band-aid — it helps at boundaries but also increases index size and can introduce duplicate context in the model's prompt
  • Chunk size trade-off — smaller chunks = better retrieval precision, worse context (model sees fragment). Larger chunks = more context, lower precision (irrelevant content dilutes)
  • Metadata per chunk — always store: source doc, page number, section title, doc date. Without these you can't filter, cite, or detect stale content
  • Hierarchical is underused — retrieve the small chunk (512 tokens), return its parent section (2048 tokens) to the LLM. Best precision + context combo

Python · LangChain splitters with metadata preservation
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain.retrievers import ParentDocumentRetriever
from langchain_community.storage import InMemoryStore

# Child chunks: small, precise, for retrieval
child_splitter = RecursiveCharacterTextSplitter(
    chunk_size=400,
    chunk_overlap=50,
    separators=["\n## ", "\n### ", "\n\n", "\n", ". ", " "],
)
# Parent chunks: larger, for context returned to the LLM
parent_splitter = RecursiveCharacterTextSplitter(
    chunk_size=2000,
    chunk_overlap=100,
    separators=["\n## ", "\n\n"],
)

# ParentDocumentRetriever: indexes child chunks,
# but returns the parent when a child matches
retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=InMemoryStore(),       # swap for Redis/DB in prod
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
)
retriever.add_documents(docs, ids=None)

# Retrieval: finds small, precise chunk; returns full section
results = retriever.invoke("What is the FMLA eligibility requirement?")
  • How do you decide what chunk size to use?
    Start with the document structure, not a number. If the documents have clear sections (headings, numbered policies), split on those boundaries first — the document's own structure is the best chunker. If it's free-form prose, 400-600 tokens with 10-15% overlap is a reasonable starting point. Then run RAGAS context recall on 20-30 representative queries: if it's below 0.8, your chunks are probably too large (irrelevant content) or the boundary is wrong. If faithfulness is low, chunks may be too small and the model is stitching together fragments. Iterate from there — chunk size is a hyperparameter, not a constant.
  • What's the failure mode of too much chunk overlap?
    Two problems. First, index bloat — 20% overlap means 20% more vectors to search, which slows retrieval and increases cost. Second, and worse: when you retrieve the top-K chunks and two of them heavily overlap, the model's context window gets filled with near-duplicate content. You've wasted context space that could have gone to a different relevant document. In one case I saw the same paragraph appear 3 times in a 4-chunk result set — the model cited "multiple sources" that were all the same source. Set overlap to the minimum needed to avoid mid-sentence splits (usually 30-80 tokens), not a percentage of chunk size.
Embedding & IndexingModel selection · Domain mismatch · Vector stores
The embedding model determines how well semantic similarity maps to actual relevance in your domain. A model trained on web text may rank "employee handbook" and "HR policy guide" as distant — because in its training data they were different topics.
ModelStrengthsWatch out for

War Story Pattern — Domain Mismatch Built an NFL Gamebook RAG using text-embedding-3-small. Queries about "third down conversion rate in the red zone" scored poorly against chunks that said "3rd-and-goal efficiency inside the 20." The model hadn't seen much football statistics text — these phrases weren't semantically close in its embedding space. Added BM25 alongside dense vectors (hybrid search) to catch exact-term matches. Alternatively, fine-tuning the embedding model on domain text improved recall by 18%, but added 2 weeks of work. Hybrid was faster to ship.
  • Embedding model ≠ LLM — you can use different models for each step; the embedding model just needs to produce good similarity scores for your domain
  • Re-indexing cost — changing embedding models means re-embedding every chunk; plan for this before picking a model. Lock the model version in config.
  • Dimensionality — higher dims = more expressive but slower search; pgvector and most hosted stores handle up to 1536 comfortably; 3072 dims may need HNSW tuning
  • Databricks AI Search — fully managed vector index in Unity Catalog; integrates with Model Serving embeddings; Delta Sync keeps index current as tables update

  • How do you handle stale documents in your index?
    Metadata filtering is the first line of defense — store doc_date on every chunk and filter at query time to only retrieve documents from the current plan year. But filtering alone isn't enough: the stale doc is still in the index and will appear in unfiltered queries. The right fix is a deletion strategy: when a document is superseded, mark it deleted in the source table. With Databricks AI Search Delta Sync, the deletion propagates to the index automatically on the next sync. For self-managed vector stores, you need an explicit delete by chunk_id, which requires you to have tracked which chunk_ids came from which source document — another reason to store source metadata at ingest time.
  • When would you NOT use a cloud embedding model?
    Three cases: (1) Data cannot leave the VPC — clinical trial data, PII-heavy HR records, proprietary formulations. Run a self-hosted model (nomic-embed, e5-large) inside your network. (2) Cost at scale — embedding 50M product descriptions daily at $0.00002/1K tokens adds up; a local model on GPU may be cheaper at that volume. (3) Latency is critical — a round-trip to an embedding API adds 50-200ms; for real-time search, a local model with sub-10ms inference is worth the quality trade-off. In most cases, a hosted model is the right default — the cost and ops savings outweigh the edge cases.
Hybrid SearchDense + BM25 · RRF · Reranking
Dense vector search finds semantically similar content. BM25 finds exact keyword matches. Neither alone is enough. Hybrid combines both — and a reranker makes the final call on which retrieved chunks are actually relevant.
  • Dense-only fails on keywords — "COBRA continuation coverage" is a legal term. Dense vectors may embed it near "health insurance continuation" — but if the doc uses the exact phrase, BM25 finds it in one shot
  • BM25-only fails on synonyms — "time off" vs "PTO" vs "vacation leave" — BM25 requires the exact term; dense vectors find all three as semantically equivalent
  • Reciprocal Rank Fusion (RRF) — merge dense and BM25 result lists by combining their rank positions (not scores). Simple, no hyperparameter tuning. Works well as a baseline.
  • Reranker — a cross-encoder model (e.g. Cohere Rerank, BGE Reranker) scores each query+chunk pair together, not independently. Much more accurate than cosine similarity alone. Adds 100-300ms latency. Use on top-20 candidates before returning top-5 to the LLM.
  • When hybrid pays off most — product codes, drug names, policy numbers, legal citations, acronyms. Any domain with precise terminology that must be matched exactly.
When to add BM25 First signal: users ask "why didn't it find the exact section I was looking for?" or RAGAS context recall is above 0.8 but answer correctness is below 0.7 on queries with specific terms. Dense search retrieved topically related chunks but missed the exact policy clause. BM25 hybrid fixed it in 2 hours — no re-indexing required.
Python · LangChain EnsembleRetriever: BM25 + Dense with RRF
from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import Chroma

# Load same chunks into both retrievers
bm25_retriever = BM25Retriever.from_documents(docs)
bm25_retriever.k = 10

vectorstore = Chroma.from_documents(docs, OpenAIEmbeddings())
dense_retriever = vectorstore.as_retriever(search_kwargs={"k": 10})

# EnsembleRetriever uses RRF to merge results
# weights=[0.4, 0.6]: trust dense more for semantic queries
# flip to [0.6, 0.4] for keyword-heavy domains (legal, medical codes)
hybrid_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, dense_retriever],
    weights=[0.4, 0.6],
)

# Optional: add a reranker on top
from langchain.retrievers.contextual_compression import ContextualCompressionRetriever
from langchain_cohere import CohereRerank

reranker = CohereRerank(model="rerank-english-v3.0", top_n=5)
final_retriever = ContextualCompressionRetriever(
    base_compressor=reranker,
    base_retriever=hybrid_retriever,
)
  • Why did you switch from pure vector search to hybrid? What broke?
    Users were asking very specific questions — "what's the out-of-pocket maximum for the Cigna Select plan" — and the retriever kept returning chunks about out-of-pocket maximums in general, not the specific plan. The dense embeddings treated "Cigna Select" as just another health plan name; they all lived near each other in embedding space. BM25 matched "Cigna Select" as an exact phrase in one retrieval call. Adding BM25 with a 0.5/0.5 weight split solved the precision problem. I then tuned the weights — increased BM25 to 0.6 — because this domain (insurance plans) has a lot of product-name specificity that dense search consistently misses.
  • What's the difference between a reranker and changing your top-K?
    Increasing top-K retrieves more candidates but doesn't change their ranking — you just give the LLM more text, including more irrelevant text, which increases noise and cost. A reranker re-scores every candidate by evaluating the query and chunk together (cross-encoder), not separately. It's fundamentally more accurate because it sees the relationship between query and chunk, not just their independent embeddings. The cost: one inference per candidate. So you retrieve top-20 cheap with cosine similarity, then rerank to top-5 with the cross-encoder. The LLM sees a much cleaner, more relevant context window.
Generation & FaithfulnessPrompt design · Grounding · Hallucination · Citations
Even perfect retrieval fails if the LLM ignores the context and answers from parametric memory. Prompt design, grounding instructions, and citation requirements are the levers.
  • Model ignores context — "answer only from the provided documents" isn't enough. The model's parametric knowledge is strong and will fill gaps even when told not to. Require a citation for every claim.
  • Context ordering matters — LLMs have a "lost in the middle" problem: they pay most attention to the beginning and end of the context. Put the most relevant chunk first, not last.
  • Conflicting context — two retrieved chunks say different things (e.g., 2023 vs 2024 deductible). Without date metadata, the model picks one arbitrarily. Fix: include doc_date in the chunk header; instruct the model to prefer the most recent.
  • Unanswerable questions — if the answer isn't in the retrieved context, the model should say so. Default behavior is to hallucinate a plausible answer. Add explicit instruction: "If the answer is not in the provided documents, say 'I don't have that information' — do not guess."
  • Citations prevent silent hallucination — requiring the model to cite a source doc and page number forces it to ground its answer. If it can't cite, it can't answer. This catches hallucinations before users do.
Lost in the Middle Liu et al. (2023) showed that LLMs perform significantly worse when the relevant document is in the middle of a long context vs. at the beginning or end. Practical fix: put highest-scored chunks first, not in a random order. A reranker helps here too — its output order is already relevance-ranked.
Python · RAG prompt with grounding + citation requirement
RAG_SYSTEM_PROMPT = """You are an HR benefits assistant. Answer questions only
using the provided document excerpts. Follow these rules strictly:

1. If the answer is in the documents, cite the source: [Doc: {source}, p.{page}]
2. If the documents contain conflicting information, cite both and prefer the
   more recent document (higher doc_year).
3. If the answer is NOT in the provided documents, respond exactly:
   "I don't have that information in the current benefits documents."
   Do NOT guess, infer, or use general knowledge about benefits.
4. Keep answers concise — 2-4 sentences unless the user asks for detail."""

def build_rag_prompt(query: str, chunks: list[dict]) -> list[dict]:
    # Put highest-relevance chunk first (lost-in-middle fix)
    context = "\n\n".join(
        f"[Doc: {c['source_doc']}, Year: {c['doc_year']}, p.{c['page']}]\n{c['text']}"
        for c in chunks  # already ranked by reranker
    )
    return [
        {"role": "system", "content": RAG_SYSTEM_PROMPT},
        {"role": "user",   "content": f"Documents:\n{context}\n\nQuestion: {query}"},
    ]
  • The model keeps answering from general knowledge instead of the documents. How do you fix it?
    Three things in combination. First, require citations in the system prompt — "every claim must be followed by [Doc: X, p.Y]." A model that can't cite can't answer. This single change cut hallucination rate significantly in my experience because it forces the model to verify its claim against the context before producing it. Second, when there's no relevant context, the model should fail loudly: give it an explicit escape hatch phrase ("I don't have that information") and few-shot examples of it being used. Third, if the model is still pulling from parametric memory, lower temperature to 0 — deterministic generation is less likely to creatively fill gaps. If all else fails, the retrieval is probably missing the relevant doc — check recall first before debugging generation.
RAG Evals & IterationRAGAS · Faithfulness · Context Recall · Precision
You cannot improve what you don't measure. RAGAS gives you four independent signals across the pipeline — each one points to a different layer to fix. The eval loop is the job: measure, diagnose, fix, re-measure.
RAGAS MetricWhat it measuresLow score → fix
FaithfulnessAre the answer's claims grounded in the retrieved context?Generation prompt; model ignoring context; hallucination
Answer RelevanceDoes the answer actually address the question asked?Retrieval returning off-topic chunks; prompt not focusing model
Context RecallDid retrieval find the chunks that contain the ground-truth answer?Chunking strategy; embedding model; missing docs in index
Context PrecisionOf the retrieved chunks, what fraction were actually useful?Top-K too large; retrieval returning noise; reranker needed
The LLM-as-Judge Trap Using the same model to generate answers AND judge their faithfulness is circular. The judge model gives higher scores to outputs that resemble its own generation style — it's not measuring ground truth, it's measuring self-consistency. Use a different, typically stronger model as the judge (e.g., generate with Claude Haiku, judge with Claude Sonnet). Or use RAGAS with a judge model different from your generation model.
  • Start with context recall — if retrieval isn't finding the right docs, nothing downstream matters. Fix retrieval first, then evaluate generation.
  • 20-30 golden questions — manually create a test set of representative questions with known correct answers. Your eval is only as good as this set.
  • Regression testing — every chunking or prompt change should be run against the full eval set, not just the cases that motivated the change
  • Business metric ≠ RAGAS metric — track both. A 0.92 faithfulness score with 40% user satisfaction means the questions in your eval set don't represent real user queries
Python · RAGAS evaluation with separate judge model
from ragas import evaluate, EvaluationDataset
from ragas.metrics import faithfulness, answer_relevancy, context_recall, context_precision
from ragas.llms import LangchainLLMWrapper
from langchain_anthropic import ChatAnthropic

# Use a DIFFERENT model as judge than the one that generated answers
# Prevents self-consistency bias inflating scores
judge_llm = LangchainLLMWrapper(ChatAnthropic(model="claude-sonnet-4-5"))

dataset = EvaluationDataset.from_list([
    {
        "user_input":           "What is the PPO deductible for 2026?",
        "response":             "The 2026 PPO deductible is $1,500 for individual coverage.",
        "retrieved_contexts":   ["...PPO plan: $1,500 individual deductible..."],
        "reference":            "The individual deductible for the PPO plan in 2026 is $1,500.",
    },
    # ... 20-30 more golden Q&A pairs
])

results = evaluate(
    dataset=dataset,
    metrics=[faithfulness, answer_relevancy, context_recall, context_precision],
    llm=judge_llm,
)
df = results.to_pandas()
print(df[["faithfulness", "answer_relevancy", "context_recall", "context_precision"]].mean())
  • Your evals were coming back poorly. Walk me through what you did.
    First thing: look at each metric independently, not just the average. Context recall was 0.61 — that told me retrieval was the problem, not generation. I sampled 10 failing queries and looked at what was actually retrieved vs. what the ground truth answer required. Pattern: the right chunk existed in the index but ranked 8th or 9th — outside the top-5 I was returning. Two causes: chunk boundaries were wrong (the relevant sentence was split across two chunks, scoring lower than a full-context chunk), and pure dense search was missing keyword-specific queries. Fixed chunking boundaries first, then added BM25 hybrid. Recall went to 0.84. Faithfulness was already fine — generation was doing its job once retrieval fed it the right context.
  • How do you create a good golden eval set?
    This is harder than the code. A few principles: (1) Sample from real user queries, not queries you'd think to ask — if users ask "can I use FSA money for sunscreen?" your golden set needs that, not just textbook benefit questions. (2) Cover edge cases explicitly: questions where the answer requires combining two chunks, questions where the answer is NOT in the documents, questions with ambiguous terms. (3) Have domain experts verify the ground truth answers — HR attorneys for benefits, clinical pharmacists for drug data. Wrong ground truth = misleading eval. (4) Create a regression subset of 10-15 queries that previously failed — run this on every change to make sure you're not breaking what you fixed.
