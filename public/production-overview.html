Latency & P99Cold starts · TTFT · Token budget · P50 vs P99
P50 latency is what your system does on a good day. P99 is what users experience when something is slightly wrong. AI systems have latency distributions that are much wider than traditional APIs — a 2s P50 can have a 14s P99.
Latency componentTypical rangePrimary lever
Embedding (query)20–150msCache frequent queries; batch embed; self-host for <10ms
Vector search10–200msHNSW tuning; approximate search; warm index
Reranking100–400msRerank top-20 only, not top-100; run async if possible
LLM TTFT (time to first token)200ms–3sStreaming; smaller model for drafts; prompt caching
LLM generation (full response)1s–15sReduce max_tokens; smaller model; streaming UX
Cold start (serverless)2s–10s addedPre-warm containers; provisioned concurrency; keep-alive pings
War Story — P99 Disaster Launched an HR chatbot with P50 = 1.8s — acceptable. First week in production, P99 was 14.2s. Users were abandoning queries. Root cause: cold starts on the embedding model container (serverless Lambda). The container had a 6–8s startup time. Fixed with two changes: (1) provisioned concurrency on the embedding endpoint to keep 2 containers warm at all times; (2) separated the fast path (cached frequent queries) from the slow path (cold retrieval), so 80% of queries hit cache at <200ms. P99 dropped to 3.1s.
  • Measure TTFT separately — time-to-first-token is the user's perceived latency when streaming; optimize this over total response time
  • Prompt caching — Anthropic and OpenAI cache the system prompt portion when it's long (>1K tokens); subsequent calls reuse the KV cache, cutting TTFT by 30–60%
  • Token budget for agents — unbounded agent loops have unbounded latency; set a max_tokens budget per turn AND a max_steps budget per run
Python · Latency instrumentation + prompt cache headers
import time
import anthropic
import mlflow

client = anthropic.Anthropic()

def timed_invoke(messages: list, system: str) -> dict:
    t0 = time.perf_counter()
    first_token_time = None

    with client.messages.stream(
        model="claude-sonnet-4-5",
        system=system,
        messages=messages,
        max_tokens=1024,
    ) as stream:
        for chunk in stream:
            if first_token_time is None and hasattr(chunk, "delta"):
                first_token_time = time.perf_counter() - t0
        final = stream.get_final_message()

    total_time = time.perf_counter() - t0
    usage = final.usage

    mlflow.log_metrics({
        "ttft_ms":          (first_token_time or 0) * 1000,
        "total_latency_ms": total_time * 1000,
        "input_tokens":     usage.input_tokens,
        "output_tokens":    usage.output_tokens,
        "cache_read_tokens": getattr(usage, "cache_read_input_tokens", 0),
    })
    return {"content": final.content[0].text, "latency_ms": total_time * 1000}
  • P50 was fine but P99 was 14 seconds. Walk me through how you diagnosed it.
    First, segment the latency into components — embedding, retrieval, reranking, LLM. I added timing spans to each step and looked at the P99 distribution per component. The embedding step had a bimodal distribution: 80ms (fast) and 7,000ms (slow). That's a cold start signature, not a throughput problem. Confirmed by correlating slow requests with container init events in CloudWatch — any request that hit an unwarmed container paid the 6–8s startup cost. Fix: provisioned concurrency to keep 2 containers always warm. For the remaining P99 budget, added semantic caching (cache the embedding + top-K chunks for semantically similar queries) — hit rate of ~35% for frequent HR questions, those now return in under 200ms. P99 went from 14.2s to 3.1s.
Cost ManagementToken costs · Caching · Model tiering · Batching
LLM costs scale with tokens × requests. An agent that loops 10 times per query costs 10× what a single-call chain costs. Cost management is an architectural decision, not an ops task.

Prompt / KV caching30–80% on repeated system promptsSystem prompt must be long (>1K tokens) and stable; cache TTL varies by provider
Semantic query cache20–50% on repetitive user queriesCache invalidation on doc updates; similarity threshold tuning

War Story — Runaway Agent Cost An agent processing NFL Gamebook questions looped 47 times on a single ambiguous query — "compare Manning's stats across all playoff appearances." Each loop called the embedding model + LLM. Single request cost: $2.14. At 500 queries/day that's $1,070/day. Added a max_steps=12 hard stop and a per-request token budget of 8,000 tokens. Cost dropped to $0.08/query. The hard stop also revealed the underlying problem: the query was too broad for the tool definitions; the agent was looping because no single tool could answer it. Split into a structured query pre-processor that broke broad queries into bounded sub-queries before the agent ran.

def route_by_complexity(query: str) -> str:
    """Route to cheaper model for simple lookups."""
    simple_patterns = ["what is", "when is", "how many", "who is"]
    if any(query.lower().startswith(p) for p in simple_patterns) and len(query) < 80:
        return "claude-haiku-4-5"      # ~20x cheaper than Sonnet
    return "claude-sonnet-4-5"        # complex reasoning, synthesis

# Per-request cost tracking
def estimate_cost(input_tokens: int, output_tokens: int, model: str) -> float:
    rates = {
        "claude-haiku-4-5":   (0.80, 4.00),   # per 1M tokens (in, out)
        "claude-sonnet-4-5":  (3.00, 15.00),
    }
    r_in, r_out = rates.get(model, (3.0, 15.0))
    return (input_tokens * r_in + output_tokens * r_out) / 1_000_000
  • Your LLM spend tripled in a week. How do you debug it?
    Pull the MLflow trace data — every request logs input_tokens, output_tokens, model, and step_count. Group by: (1) model — did someone switch from Haiku to Sonnet? (2) step_count — are agents looping more? (3) input_tokens — did a prompt change add 2K tokens to every request? (4) query pattern — is one specific user or workflow generating disproportionate cost? In the runaway agent case, the grouping by step_count immediately showed a tail of requests at 40+ steps — normal was 3–8. Found the problematic query pattern in 10 minutes. Without per-request token logging, this would have taken days of guesswork.
StreamingSSE · Partial responses · Tool call streaming · Failure modes
Streaming dramatically improves perceived latency — users see the first token in 300ms instead of waiting 5s for the full response. But streaming adds complexity: partial state, tool calls mid-stream, and disconnect handling all require explicit design.
  • SSE (Server-Sent Events) — the protocol for streaming LLM responses; each chunk is a data: {...} line; the client accumulates text as it arrives
  • Tool calls interrupt the stream — when the model decides to call a tool mid-generation, the text stream stops; tool is executed; then generation resumes; the UI must handle this transition
  • Buffering at the API gateway — if your reverse proxy or API gateway buffers responses, streaming is silently broken; users see the full response arrive at once after the full generation completes. Must configure proxy_buffering off (nginx) or equivalent
  • Client disconnect handling — if the user closes the browser mid-stream, the LLM API keeps generating and billing; add AbortController on the client and server-side request cancellation
  • Partial state display — streaming JSON or structured output is tricky; display intermediate markdown, not raw partial JSON that renders as broken UI
War Story — Buffered Gateway Built streaming support, tested locally — worked perfectly. Deployed behind an AWS Application Load Balancer. All streaming queries now took the full generation time before any response appeared. ALB was buffering the entire response before forwarding. Fix: set idle_timeout to 300s, added X-Accel-Buffering: no header on streaming responses, switched to ALB streaming mode. Took 2 days to diagnose because the behavior was correct locally and only appeared behind the load balancer.
Python · FastAPI streaming endpoint with tool call handling
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import anthropic, json

app = FastAPI()
client = anthropic.Anthropic()

async def stream_response(query: str):
    with client.messages.stream(
        model="claude-sonnet-4-5",
        messages=[{"role": "user", "content": query}],
        max_tokens=1024,
    ) as stream:
        for text_chunk in stream.text_stream:
            # SSE format: each chunk as a data event
            yield f"data: {json.dumps({'text': text_chunk})}\n\n"
        # Signal completion
        yield "data: [DONE]\n\n"

@app.get("/stream")
async def stream_endpoint(query: str):
    return StreamingResponse(
        stream_response(query),
        media_type="text/event-stream",
        headers={
            "X-Accel-Buffering": "no",         # disable nginx buffering
            "Cache-Control":      "no-cache",
            "Connection":         "keep-alive",
        },
    )
  • Streaming worked in local testing but not in production. What do you check?
    Check the full request path in order: (1) API gateway or load balancer — most ALBs and API Gateways buffer by default; need explicit streaming config. (2) Reverse proxy — nginx proxy_buffering off and proxy_read_timeout long enough for slow generations. (3) CDN — if there's a CDN in front, it almost certainly buffers; disable caching for streaming routes. (4) Application server — WSGI servers (Gunicorn) don't support streaming well; need ASGI (Uvicorn/Hypercorn) with async generators. (5) Client — browser fetch with proper SSE parsing or EventSource. The ALB buffering case is the most common and most surprising — it looks like a latency problem, not a streaming problem, because you eventually get the response.
Deployment & DriftBlue/green · Shadow mode · Model version pinning · Rollback
AI systems drift in ways traditional software doesn't: model provider updates, embedding model changes, document corpus changes, and query distribution shifts can all degrade quality silently without any code change on your part.
Drift typeCauseDetectionFix
Model driftProvider updates model silently (e.g., gpt-4 → gpt-4-0125)Automated eval regression alertPin model version; pin date in API call
Data driftNew documents ingested with different format or qualityParse quality score at ingest; online faithfulness monitoringIngest validation pipeline; per-doc quality gate
Query driftUsers start asking new types of questions not in eval setCluster new queries; compare to eval set coverageAdd new query types to eval set; expand training examples
Embedding driftEmbedding model updated; embeddings in index now inconsistentRetrieval quality drop; mismatched vector dimensionsAlways re-index from scratch when changing embedding model
War Story — Silent Model Update Pinned to "gpt-4" in the API call — thought this was stable. The provider updated the model underneath the same API alias. Automated eval caught a 0.08 drop in faithfulness 12 hours after the update. Didn't know the model had changed until we checked the model version in the API response headers. Now always pin with a date: "gpt-4-0125-preview" or "claude-sonnet-4-5-20251001". Never use an alias without a version.
  • Blue/green deployment — two identical environments; route 100% traffic to one; update the other; shift traffic; instant rollback by shifting back
  • Shadow mode — run the new version in parallel with production, compare outputs without affecting users; best for validating model or prompt changes before promotion
  • Canary release — shift 5% of traffic to new version; monitor quality metrics for 24h; promote or revert based on data
  • Model version pinning — always specify the full model version string including date; log the model version used in every MLflow trace; test upgrades explicitly before promoting
  • Rollback plan — keep the previous prompt version and model version in config; rollback = config change, not code deployment
  • How do you deploy a prompt change safely?
    Three-stage process. Stage 1: offline eval — run the new prompt against the full RAGAS eval suite in a branch; must match or improve on all metrics, no regressions on the regression subset. Stage 2: shadow mode — deploy the new prompt alongside production for 48 hours; route all requests to both versions; compare faithfulness scores and answer length on live traffic without users seeing the new version. Stage 3: canary — shift 5% of live traffic to the new prompt; monitor online metrics for 24 hours; if no degradation, promote to 100%. Any failure at any stage reverts to the previous prompt version, which takes 30 seconds — it's a config value, not a code deployment. This process sounds heavy but it's saved us from three significant regressions that looked fine in manual testing.

Python · MLflow-based monitoring dashboard query (Databricks SQL)
-- Databricks SQL: query system.agent_traces for production health
-- Run as a scheduled job every 15 minutes; alert on threshold breach

SELECT
    date_trunc('hour', timestamp)           AS hour,
    count(*)                                  AS total_requests,
    avg(execution_time_ms)                    AS avg_latency_ms,
    percentile(execution_time_ms, 0.99)      AS p99_latency_ms,
    sum(CASE WHEN status = 'ERROR' THEN 1 ELSE 0 END) AS errors,
    avg(input_tokens + output_tokens)         AS avg_tokens_per_request,
    avg(faithfulness_score)                   AS avg_faithfulness
FROM system.agent_traces
WHERE timestamp >= current_timestamp() - INTERVAL 24 HOURS
  AND app_name = 'hr-rag-chatbot'
GROUP BY 1
ORDER BY 1 DESC

-- Alert rule: if avg_faithfulness < 0.75 in last 2 hours, page on-call
  • What do you put in your AI system runbook for on-call?
    Six sections. (1) System overview: what the system does, who uses it, what breaks if it's down. (2) Alert definitions: what each alert means, which are P1 (page immediately) vs P2 (fix next business day). (3) Diagnosis playbook: for each alert, the first 3 things to check — e.g., faithfulness alert → check ingest logs for new doc format, check model version in traces, check retrieval scores on the failing queries. (4) Known failure modes: escalation rate spike usually means data ingestion issue, not generation; cost spike usually means agent loop, check step_count distribution. (5) Rollback procedure: exactly how to revert to previous prompt/model version, who approves it, how long it takes. (6) Escalation contacts: who to call if the on-call engineer can't resolve in 30 minutes.
Scaling & Rate LimitsRate limits · Queuing · Autoscale · Throttling
LLM APIs have rate limits measured in tokens-per-minute and requests-per-minute. At scale, hitting these limits is a production outage. Rate limit management is infrastructure, not an afterthought.
  • TPM vs RPM limits — tokens-per-minute is usually the binding constraint; a batch of long documents can hit TPM even at low RPM; measure both separately
  • Exponential backoff with jitter — when hitting a 429, retrying immediately makes it worse (thundering herd); add random jitter (0.5–1.5× base delay) to spread retries
  • Request queuing — for batch workloads, queue requests and drain them at a controlled rate below the limit; don't fire all requests simultaneously
  • Multiple API keys / accounts — for very high throughput, spread load across multiple accounts; coordinate rate limits at the queue layer
  • Databricks Model Serving autoscaling — define min/max concurrent requests per endpoint; scales to zero when idle (cost efficient); configure scale-up time to match latency requirements
War Story — Batch Job Rate Limit Storm Launched a nightly batch job to re-embed 50K benefit document chunks after a corpus update. Job fired all 50K embedding requests simultaneously. Hit the 60 RPM limit in 2 seconds; 429s for the next 14 minutes; job took 6 hours instead of 30 minutes. Fixed with a token bucket rate limiter: max 50 requests/sec with burst of 100. Job now completes in 18 minutes reliably.
Python · Token bucket rate limiter for batch embedding
import asyncio, time
from collections import deque

class RateLimiter:
    def __init__(self, max_rate: float, burst: int = 1):
        self.max_rate = max_rate   # requests per second
        self.burst    = burst
        self.tokens   = float(burst)
        self.last     = time.monotonic()

    async def acquire(self):
        while True:
            now = time.monotonic()
            self.tokens = min(self.burst, self.tokens + (now - self.last) * self.max_rate)
            self.last = now
            if self.tokens >= 1:
                self.tokens -= 1
                return
            wait = (1 - self.tokens) / self.max_rate
            await asyncio.sleep(wait)

limiter = RateLimiter(max_rate=40, burst=80)  # conservative vs 60 RPM limit

async def embed_with_limit(text: str) -> list[float]:
    await limiter.acquire()
    return embedding_client.embed(text)
  • How do you handle LLM API rate limits in a multi-tenant system?
    Three layers. First, fair queuing at the application layer — each tenant gets a share of the rate limit budget; high-priority tenants (e.g., paying customers) get a larger share; requests from over-quota tenants are queued with a max wait time before returning a 503. Second, adaptive throttling — track the rolling token usage per minute; when usage approaches 80% of the limit, slow down proactively rather than waiting for a 429. Third, circuit breaker — if we get three consecutive 429s in a 10-second window, open the circuit for 30 seconds and return a graceful degradation response ("system is busy, please retry in 30 seconds") rather than queuing indefinitely. The combination prevents the thundering herd that makes rate limit recovery take much longer than the original limit window.
