Agent PatternsReAct · Plan-Execute · Supervisor/Worker
An agent is an LLM that decides what action to take next, executes it, observes the result, and repeats. The pattern determines how much the agent plans upfront vs. reasons step-by-step.
Three Core Patterns
PatternHow it worksBest for
ReActReason → Act → Observe → repeat in a loop. LLM decides each tool call based on prior observations.Open-ended tasks where the path is unknown upfront. Customer support, research, debugging.
Plan-and-ExecuteLLM generates a full plan first, then a separate executor runs each step. Replanning if a step fails.Long-horizon tasks with predictable steps. Report generation, data pipelines.
Supervisor/WorkerSupervisor LLM routes tasks to specialized sub-agents. Each worker has its own tools and state.Multi-domain tasks. FFF's OS&D: supervisor routes to SAP, Warehouse, FedEx, Video agents.
Director Answer — "What agent pattern do you use and why?" Start with the problem: single-domain or multi-domain? Known steps or dynamic? Then map to pattern. For FFF's claims: multi-domain (SAP, Warehouse, FedEx, Video) + parallel sub-tasks → Supervisor/Worker. For open research tasks: ReAct. For structured pipelines with audit requirements: Plan-and-Execute (the plan is the audit trail).
  • ReAct — most flexible, highest token cost, can loop indefinitely without guardrails
  • Plan-Execute — more predictable, cheaper per run, but rigid; bad at handling unexpected results mid-plan
  • Supervisor/Worker — scales to complex domains; sub-agents can run in parallel; each worker is independently testable
  • When to mix — supervisor can use ReAct to route, while individual workers use Plan-Execute internally
ReAct Agent with LangGraph
Python · create_react_agent — simplest path to a working agent
from langchain_anthropic import ChatAnthropic
from langchain_core.tools import tool
from langgraph.prebuilt import create_react_agent

@tool
def lookup_claim(claim_id: str) -> dict:
    """Look up OS&D claim details from SAP."""
    # In production: call SAP API
    return {"claim_id": claim_id, "status": "open", "amount": 1250.00}

@tool
def check_warehouse(order_id: str) -> dict:
    """Check warehouse scan records for an order."""
    return {"scanned": True, "location": "Bay 12", "timestamp": "2026-08-09T14:32"}

llm = ChatAnthropic(model="claude-sonnet-4-5")
agent = create_react_agent(llm, tools=[lookup_claim, check_warehouse])

result = agent.invoke({
    "messages": [{"role": "user", "content": "Investigate claim OS-2026-881"}]
})
# Agent reasons: "I should look up the claim first"
# → calls lookup_claim("OS-2026-881")
# → observes result → calls check_warehouse("ORD-4491")
# → synthesizes final answer
  • What's the difference between a chain and an agent?
    A chain has a fixed sequence of steps determined at design time — you know exactly what runs and in what order. An agent is dynamic: the LLM decides at each step what tool to call next based on what it observed. Chains are predictable and cheap; agents are flexible but can loop, hallucinate tool calls, or take unexpected paths. In practice, use chains for well-defined workflows and agents when the path depends on external data you can't predict.
  • When would you NOT use an agent?
    When the task has a known, fixed sequence of steps — use a chain or pipeline instead. Agents add latency (multiple LLM calls), cost (tokens per reasoning step), and unpredictability. For example, a structured ETL job that always runs ingest → transform → load → notify has no need for dynamic routing. Agents shine when the path genuinely depends on what the system discovers during execution.
  • How does FFF's AgentBricks use the Supervisor/Worker pattern?
    FFF's Supervisor Agent receives a claim from the BioSupply portal via Salesforce. It routes to 5 specialized sub-agents in parallel — SAP (order status), Warehouse (scan records), Salesforce (CRM history), FedEx (carrier tracking), and Video (packing station footage). Each sub-agent runs independently and returns a structured result. The Supervisor then scores confidence across all results; if confidence is below threshold, it escalates to a human. If high confidence, the Summary Agent writes the resolution back to Salesforce. This cut resolution time from 10+ days to 1-3 minutes.
Tool Use & Function Calling@tool · Parallel · Schema Design
Tools are the bridge between LLMs and the real world. The LLM generates a structured tool call (JSON); your code executes it and returns the result. Schema design is critical — a poorly described tool leads to wrong or missed calls.
  • Tool = function + schema — the schema (JSON Schema) is what the LLM sees; the function is what your code runs. Write schemas for the model, not for the implementation.
  • Description is the prompt — the tool's docstring IS the instruction to the model. Be explicit: "Call this when the user asks about shipment status. Do not call for billing questions."
  • Parallel tool calls — modern models (GPT-4o, Claude Sonnet) can call multiple tools simultaneously. LangGraph's ToolNode handles parallel calls automatically.
  • Tool errors — if a tool raises an exception, the agent receives the error message as an observation and can retry or route differently. Don't let errors crash silently.
  • Force tool use — set tool_choice="any" or tool_choice={"type":"tool","name":"X"} to guarantee the model calls a tool (useful for structured extraction).
Common Mistake Vague tool descriptions. "Gets order info" → model doesn't know when to call it. Better: "Retrieves SAP order status, line items, and ship date for a given order_id. Call this first when investigating any OS&D claim."
Tool Definition + Parallel Execution

from langchain_core.tools import tool
from pydantic import BaseModel, Field

# Structured input schema — more reliable than free-text args
class ClaimInput(BaseModel):
    claim_id: str = Field(description="OS&D claim ID, format OS-YYYY-NNN")
    include_history: bool = Field(default=False, description="Include 90-day claim history")

@tool("lookup_osd_claim", args_schema=ClaimInput)
def lookup_osd_claim(claim_id: str, include_history: bool = False) -> dict:
    """Retrieve OS&D claim details from SAP.
    Call this first when investigating any damage or shortage claim.
    Do NOT call for billing disputes or returns — use lookup_billing instead."""
    return sap_client.get_claim(claim_id, include_history=include_history)

from langgraph.prebuilt import ToolNode

  • How do you handle tool failures in production agents?
    Three layers: (1) At the tool level — catch exceptions, return a structured error dict like {"error": "SAP unavailable", "retry": true} rather than raising. The LLM receives this as an observation and can decide to retry or route differently. (2) At the graph level — add a max_retries counter in state and a conditional edge that routes to a fallback node after N failures. (3) At the system level — circuit breakers around external APIs so a flaky SAP connection doesn't cascade into agent loops.
  • What's the difference between tool_choice="auto" and "required"?
    auto: the model decides whether to call a tool or respond in plain text — use this for conversational agents where not every turn needs a tool. required: the model MUST call at least one tool — use this for structured extraction pipelines where you need a guaranteed tool call (e.g., a routing step that must classify the request). {"type":"tool","name":"X"}: forces a specific tool — use for the first step of a known workflow.
Multi-Agent SystemsSupervisor · Worker · Handoffs · FFF Architecture
Multiple specialized agents coordinated by an orchestrator. Each agent owns a domain, has its own tools, and can run independently. The orchestrator decides routing, aggregation, and escalation.

  • Why parallel sub-agents? SAP, FedEx, and Warehouse lookups are independent — running sequentially adds 3-5s per call; parallel collapses to the slowest single call (~1-2s)
  • Handoff vs shared state — in LangGraph, sub-agents can share a parent state schema or use bridge functions to translate between schemas
  • Confidence gate pattern — supervisor scores each sub-agent result (did it return data? is it consistent with others?); low confidence → interrupt() for human review
  • Individual reusability — FFF's sub-agents are also callable directly from Microsoft Teams, not just through the Supervisor
Supervisor Agent with Parallel Sub-Agents
Python · LangGraph supervisor routing to parallel workers
from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, END, START
from langgraph.types import Send

class ClaimState(TypedDict):
    claim_id:   str
    sub_results: Annotated[list, operator.add]  # workers append to this
    confidence: float
    approved:   bool

def supervisor(state: ClaimState) -> list[Send]:
    # Fan out to all workers simultaneously
    return [
        Send("sap_agent",       {"claim_id": state["claim_id"]}),
        Send("warehouse_agent", {"claim_id": state["claim_id"]}),
        Send("fedex_agent",     {"claim_id": state["claim_id"]}),
    ]

def confidence_gate(state: ClaimState) -> str:
    results = state["sub_results"]
    scored = sum(1 for r in results if r.get("confidence", 0) > 0.8)
    if scored / len(results) >= 0.75:
        return "summary_agent"   # high confidence → auto-resolve
    return "human_review"      # low confidence → escalate

builder = StateGraph(ClaimState)
builder.add_node("supervisor", supervisor)
builder.add_node("confidence_gate", confidence_gate)
builder.add_conditional_edges("confidence_gate", confidence_gate,
    {"summary_agent": "summary_agent", "human_review": END})
  • How do you coordinate agents that have different state schemas?
    Use bridge functions — a wrapper node that translates between parent and child state schemas before invoking the sub-agent. In LangGraph, you compile the sub-agent graph separately, then call sub_graph.invoke({translated_state}) inside a parent node. The parent node is responsible for mapping outputs back. If schemas overlap (share some keys), you can pass shared state directly by giving both graphs the same TypedDict for those fields.
  • What's the tradeoff between a single large agent vs. multiple specialized agents?
    Single large agent: simpler to build and debug, fewer moving parts, but the context window fills up quickly with tool results, and one bad tool call can derail the whole task. Multi-agent: each worker has a focused context (only relevant tools/state), can run in parallel (faster), and failures are isolated. The cost is orchestration complexity — you need a supervisor, state merging, and inter-agent communication patterns. For FFF's use case (5 independent data sources), multi-agent was clearly right. For a simple customer support bot, a single agent is probably enough.
Memory SystemsIn-Context · External · Episodic · Semantic
Agents are stateless by default — memory is what gives them continuity. Four types serve different purposes, and the right choice depends on what needs to persist and for how long.
TypeWhat it storesLifespanLangGraph implementation
In-contextCurrent conversation messages, tool resultsSingle sessionThe messages list in State — automatic
CheckpointedFull graph state at each stepResumable across sessionsMemorySaver (in-memory) or PostgresSaver (persistent)
External / EpisodicPast conversation summaries, user preferencesPermanentStore to DB; retrieve via tool or graph entry node
SemanticFacts, domain knowledge, embeddingsPermanentVector store (AI Search, Qdrant); retrieve via RAG
  • Context window limit — in-context memory grows with each turn; for long agents, summarize or trim periodically (trim_messages)
  • Checkpointing = reproducibility — thread_id in config identifies a conversation; graph can resume exactly from any checkpoint
  • Cross-session memory — retrieve past interactions at the START of a new session via a "load_memory" node before the main agent node
  • FFF use case — the claim investigation state is checkpointed per claim_id; if a human reviewer pauses to gather more info, the agent resumes exactly where it left off

  • What's the difference between MemorySaver and PostgresSaver?
    MemorySaver stores checkpoints in RAM — fast, zero config, but lost on process restart. Use it for development and testing. PostgresSaver (or AsyncPostgresSaver) persists state to a database, surviving restarts and supporting multiple workers. In production, always use a persistent checkpointer. On Databricks, you'd use a Delta table-backed checkpointer or the managed LangGraph Platform.
  • How do you prevent context window overflow in long-running agents?
    Two strategies: (1) trim_messages(messages, max_tokens=4000) — drops oldest messages first, keeping the conversation tail. (2) Summarization node — a periodic node that compresses the message list into a short summary, replacing the raw history. LangGraph makes this clean: add a conditional edge that routes to a "summarize" node whenever len(messages) > N, then continues to the main agent node with the compressed context.
Human-in-the-Loopinterrupt() · Command(resume=) · Escalation
Production agents must be able to pause, surface a decision to a human, and resume with their input. LangGraph's interrupt() and Command(resume=) make this a first-class pattern, not a workaround.
  • When to interrupt — low confidence, irreversible actions (send email, write to DB, charge customer), regulatory requirements, or when the agent detects ambiguity it can't resolve alone
  • interrupt() pauses the graph — state is checkpointed; the agent is suspended; a payload is surfaced to the UI for human review
  • Command(resume=decision) — human's decision is sent back; graph resumes from the exact checkpoint with the human's input in state
  • Approve/reject/edit pattern — the interrupt payload contains the agent's proposed action; human can approve (proceed), reject (abort), or edit (modify the action before proceeding)
  • FFF use case — confidence gate fires interrupt() when sub-agent results are inconsistent; claims reviewer sees all evidence and either approves the AI resolution or overrides it
Regulatory Note In pharma distribution (FFF) and healthcare (Optum), some decisions legally require a human in the loop — not just for quality, but for compliance. Design interrupt points as explicit architectural components, not afterthoughts. Document them in your system design as "human decision gates."
interrupt() + Command(resume=)
Python · LangGraph HITL — pause, surface, resume
from langgraph.types import interrupt, Command

def confidence_gate_node(state: ClaimState):
    results = state["sub_results"]
    confidence = compute_confidence(results)

    if confidence < 0.75:
        # Pause graph — surfaces payload to UI
        decision = interrupt({
            "claim_id":  state["claim_id"],
            "confidence": confidence,
            "evidence":  results,
            "question":  "Insufficient confidence. Approve resolution or escalate?",
        })
        # Execution pauses HERE — resumes when human responds
        return {"approved": decision["approved"]}

    return {"approved": True}

# After human reviews in the UI:
graph.invoke(
    Command(resume={"approved": True, "reviewer": "jsmith"}),
    config={"configurable": {"thread_id": "claim-OS-2026-881"}}
)
# Graph resumes from checkpoint — decision is now in state
  • How is interrupt() different from just returning early from a node?
    interrupt() is a first-class LangGraph mechanism that checkpoints the full graph state and surfaces a payload to the calling code. The graph is genuinely suspended — not running, not polling. When Command(resume=) arrives with the human's decision, LangGraph replays from the checkpoint, injecting the decision into state. Returning early from a node doesn't preserve state or enable resumption — you'd lose all prior sub-agent results. interrupt() is the correct tool for any decision that needs to wait for external input.
  • How do you build the UI for a human-in-the-loop workflow?
    The backend streams events via astream_events(); when the stream yields an event where event["event"] == "on_chain_end" and the payload contains an interrupt, the frontend detects this sentinel and renders the approval UI (showing the evidence, proposed action, and approve/reject buttons). When the reviewer clicks approve, the frontend POSTs to an API endpoint that calls graph.invoke(Command(resume={...}), config). The backend then continues streaming the remainder of the graph execution. The thread_id ties the session together across the pause.
Reliability & FailuresLoops · Confidence Gates · Guardrails · Observability
Agents fail in ways deterministic code doesn't — infinite loops, hallucinated tool calls, inconsistent reasoning. Production reliability requires explicit guardrails, not just hope.
Failure ModeCauseFix
Infinite loopAgent keeps calling the same tool with no progressAdd step_count to state; conditional edge to END after N steps
Hallucinated tool callModel invents tool arguments or calls non-existent toolsStrict tool schemas with enum constraints; validate inputs before execution
Low confidence resolutionSub-agents return conflicting or incomplete dataConfidence gate → interrupt() for human review
Tool cascade failureOne flaky API causes the whole agent to stallTimeouts + fallback return values; circuit breaker pattern per tool
Context blowupLong agent runs fill context windowtrim_messages or summarization node
The Director Answer on Reliability "We treat agents like distributed systems — every external call can fail, loops must be bounded, and human escalation is a first-class design pattern, not an edge case. We trace every run with MLflow/LangSmith, alert on error rate and loop count, and review all human escalations weekly to improve confidence thresholds."
Loop Guard + Fallback Pattern
Python · State-based loop counter + max step enforcement
class AgentState(TypedDict):
    messages:   list
    step_count: int          # incremented by every node
    error_log:  list

def agent_node(state: AgentState):
    if state["step_count"] >= 15:
        # Hard stop — prevents runaway costs
        return {
            "messages": [{"role": "assistant",
                          "content": "Max steps reached. Escalating to human."}],
            "step_count": state["step_count"] + 1,
        }
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response], "step_count": state["step_count"] + 1}

def should_continue(state: AgentState) -> str:
    last = state["messages"][-1]
    if state["step_count"] >= 15: return "escalate"
    if hasattr(last, "tool_calls") and last.tool_calls: return "tools"
    return "end"
  • How do you test agents before deploying to production?
    Three layers: (1) Unit test individual nodes and tools with mocked LLM responses — fast, deterministic, catches logic bugs. (2) Integration test the full graph with a real (or stubbed) LLM using golden test cases — "for claim OS-2026-881, the agent should call SAP then Warehouse, then return confidence > 0.9." Track these in LangSmith eval datasets. (3) Shadow mode — run the agent in parallel with the current manual process, compare outputs without affecting production. Promote when accuracy ≥ threshold for 2 weeks.
  • A Director asks: "How do we know the agent isn't making things up?" What do you say?
    Three-part answer: (1) Tracing — every agent run is traced end-to-end (LangSmith or MLflow), so we can audit exactly what tool call returned what data and how the model used it. (2) Confidence gates — the agent scores its own certainty and escalates to a human when below threshold; we can tune this threshold by reviewing escalation cases. (3) Eval loop — we run RAGAS faithfulness scores on a sample of production traces weekly; if faithfulness drops below 0.85, we get an alert before users notice. This gives us observability, human oversight, and automated quality gates — three independent layers of assurance.
