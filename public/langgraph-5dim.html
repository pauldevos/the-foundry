StateGraph & State SchemaCore Graph · FoundationCore
The foundational class for all LangGraph workflows. State is a TypedDict whose fields are "channels" — each field has a reducer that controls how node outputs are merged. Nodes return partial dicts; unmodified keys are preserved.
State Schema with Reducers
Python · TypedDict state — the OS&D claim investigation schema
from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, END, START
from langgraph.graph.message import add_messages
from langchain_core.messages import HumanMessage, AIMessage

# Each field is a "channel" — reducer defines how updates are merged
class OSDState(TypedDict):
    messages:    Annotated[list, add_messages]    # reducer: append + dedup by .id
    claim_id:    str                               # no reducer → last-write-wins
    confidence:  float                             # no reducer → last-write-wins
    sub_results: Annotated[list, operator.add]     # reducer: list concatenation
    approved:    bool                              # no reducer → last-write-wins

builder = StateGraph(OSDState)
# ... add nodes and edges ...
graph = builder.compile()

# Invoke: pass ALL declared keys in the first call
result = graph.invoke(
    {
        "messages":    [HumanMessage("Check claim OS-2024-881")],
        "claim_id":    "OS-2024-881",
        "confidence":  0.0,
        "sub_results": [],
        "approved":    False,
    },
    config={"configurable": {"thread_id": "claim-1"}}
)

Node Returns Partial State
Python · Nodes only return keys they want to update
def sap_agent_node(state: OSDState) -> dict:
    # Read from state
    claim = state["claim_id"]
    # Call SAP API...
    sap_result = {"status": "DELIVERED", "amount": 1240.50}

    # Return ONLY what this node updates.
    # sub_results uses operator.add: this list is APPENDED to existing sub_results.
    # confidence uses last-write-wins: this value REPLACES the current confidence.
    return {
        "sub_results": [sap_result],
        "confidence": 0.92,
    }
Reducer = Merge Strategy for Each FieldWithout an Annotated reducer, returning the same key from two different nodes in the same superstep raises a conflict error. Use operator.add for lists that accumulate across nodes; use add_messages for LangChain message lists (it also deduplicates by message ID).
Parameter / ConceptDetail
TypedDictMost common state type. Each key is a channel with an optional reducer. Dataclass and Pydantic BaseModel also supported.
add_messagesLangChain reducer from langgraph.graph.message. Appends messages and deduplicates by message .id — replacing old if same id appears again.
operator.addPython built-in that concatenates lists. Use for accumulating sub-agent results across nodes. Does not deduplicate.
last-write-winsDefault when no reducer is declared. If two nodes update the same scalar field in the same superstep, LangGraph raises a MultipleWritesError.
MessagesStateBuilt-in shortcut in langgraph.graph. Equivalent to TypedDict with messages: Annotated[list, add_messages]. Extend it for additional fields.
Partial returnNodes return a dict with only the keys they modify. All other state fields are preserved from the previous checkpoint untouched.
Annotated syntaxAnnotated[list, reducer_fn] — first arg is the type, second is the reducer callable. LangGraph inspects annotations at compile time.
InitializationPass all declared keys in the first invoke() call. Missing required keys at runtime raise a KeyError when any node tries to read them.
SuperstepA round of parallel node execution. All nodes in a superstep run before reducers merge their outputs into the next state snapshot.
ChannelsLangGraph's internal name for state fields. Each channel has a reducer and a type. The term appears in error messages and advanced docs.
Do NOT Mutate State In-PlaceAlways return a new dict from a node. Mutating state["sub_results"].append(...) directly bypasses the reducer and corrupts checkpointing — the change won't appear in the next checkpoint snapshot.
Design Your State Schema FirstThe state schema is the contract between all nodes. Define it before writing any node. Fields that multiple nodes write should use a reducer (list fields almost always should). Scalar fields that only one node writes can be last-write-wins.

  • What's the difference between a reducer and last-write-wins state?
    Last-write-wins (no reducer): a node returns a value for a key and it simply replaces the previous value. Safe only when exactly one node writes to that field per superstep — otherwise LangGraph raises a MultipleWritesError. Reducer: a function that merges the new value with the existing value. operator.add for lists means each node's returned list is concatenated onto the accumulated list. This is how FFF's supervisor accumulates results from 5 parallel sub-agents — each returns a sub-result and all are concatenated safely.
  • Why does LangGraph need Annotated[list, operator.add] instead of just declaring list?
    Python TypedDict doesn't have a native way to attach merge behavior to a field. LangGraph uses Annotated as a convention: the second argument is inspected at StateGraph compile time and registered as that channel's reducer. A bare list field has no reducer — any two nodes writing to it in the same superstep will conflict. The Annotated pattern is the only way to declare reducer behavior on a TypedDict field.
  • Can nodes see each other's updates within the same superstep?
    No. All nodes in a superstep receive the SAME state snapshot (the one from the previous superstep). Their outputs are collected and reducers are applied after all of them finish. This is why fan-out works safely — parallel nodes read the same input state and their writes are merged after execution. To see another node's output, you must be in a later superstep (i.e., connected by an edge that runs after the producer node).
  • When would you use Pydantic BaseModel instead of TypedDict for state?
    Use Pydantic when you need runtime validation of state fields — e.g., ensure confidence is always between 0.0 and 1.0, or that claim_id matches a regex pattern. Pydantic also gives you default values and field aliases. The tradeoff: Pydantic adds overhead to every state update because it re-validates on each merge. For most production graphs, TypedDict is preferred for performance; add Pydantic only when input validation failures are a real operational risk.
Nodes & EdgesCore Graph · StructureCore
Nodes are plain Python functions (sync or async) that take state and return a partial state dict. Fixed edges create deterministic transitions. START and END are sentinel constants — not strings — from langgraph.graph.
Basic Node + Edge Pattern — ReAct Agent Loop
Python · Agent ↔ Tools loop with fixed edges
from langgraph.graph import StateGraph, END, START
from langgraph.graph import MessagesState
from langchain_core.messages import AIMessage

# Nodes: plain functions — read state, return partial dict
def agent_node(state: MessagesState) -> dict:
    # Call LLM with current messages
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}   # add_messages reducer appends

def tools_node(state: MessagesState) -> dict:
    # Execute tool calls from the last AI message
    tool_calls = state["messages"][-1].tool_calls
    results = [tool_executor.invoke(tc) for tc in tool_calls]
    return {"messages": results}

# Build the graph
builder = StateGraph(MessagesState)

# Register nodes
builder.add_node("agent", agent_node)
builder.add_node("tools", tools_node)

# Fixed edges — deterministic transitions
builder.add_edge(START, "agent")         # entry point (replaces set_entry_point)
builder.add_edge("tools", "agent")       # always loop back after tool execution

# Conditional edge on "agent": route to tools or end
# (covered in detail in Conditional Routing section)

# Compile
graph = builder.compile()

# Invoke
result = graph.invoke(
    {"messages": [{"role": "user", "content": "Check claim OS-2024-881"}]},
    config={"configurable": {"thread_id": "claim-1"}}
)

  • How is a LangGraph node different from a LangChain chain?
    A LangChain chain is a composition of callables — fixed, linear, DAG-only. A LangGraph node is a plain Python function that reads from and writes to a shared mutable state object. Key differences: (1) nodes can loop (chains cannot cycle); (2) nodes get the full graph state, not just the previous step's output; (3) multiple nodes can run in parallel and write to the same state (via reducers); (4) nodes can pause execution (interrupt()) and resume across process restarts. LangGraph nodes enable the stateful, cyclical patterns that production agents require.
  • What happens if a node returns an empty dict?
    Nothing changes in state — which is intentional and valid. The node still executed (consuming compute, making API calls, logging), but declared no state updates. Common pattern for notification nodes ("send Slack alert, don't update state") or guard nodes that only log. LangGraph still checkpoints after the node runs, so the execution is recorded even with an empty update.
  • How do you create a loop in LangGraph and prevent infinite execution?
    add_edge("tools", "agent") creates a cycle. To terminate: the conditional edge from "agent" must have a path that routes to END — typically when the LLM produces no more tool calls. For safety, track a step_count: int field in state and have your routing function return END when step_count > MAX_STEPS. Without a termination condition, a loop will run until the checkpointer's storage fills up or the process is killed.
  • Can you use LangGraph tools nodes from langgraph.prebuilt?
    Yes — from langgraph.prebuilt import ToolNode provides a pre-built node that executes tool calls from the last AI message, handles errors gracefully, and returns ToolMessages. It handles the boilerplate of the tools execution loop. Use it unless you need custom tool execution logic (custom error handling, conditional tool approval). create_react_agent is another prebuilt that wires agent + ToolNode automatically — useful for simple single-agent use cases.
Conditional RoutingCore Graph · Control FlowCore
Routing functions decide which node runs next based on current state. Three patterns: add_conditional_edges (route only), Command(goto=) (route + update state), and Send (parallel fan-out with per-agent state).
Pattern 1 — add_conditional_edges with path_map
Python · Classic routing: function returns string, path_map resolves to node
from typing import Literal
from langgraph.graph import StateGraph, END, START

# Routing function: inspects state, returns a string key
def route_query(state: OSDState) -> Literal["sap", "warehouse", "fedex", "end"]:
    query = state["messages"][-1].content.lower()
    if "order" in query or "sap" in query:
        return "sap"
    elif "warehouse" in query or "inventory" in query:
        return "warehouse"
    elif "fedex" in query or "carrier" in query:
        return "fedex"
    return "end"

builder.add_conditional_edges(
    "supervisor",              # source node
    route_query,               # routing function
    {                          # path_map: return_value → node_name
        "sap":       "sap_agent",
        "warehouse": "warehouse_agent",
        "fedex":     "fedex_agent",
        "end":       END,
    }
)
# If path_map is omitted: routing fn return value IS the node name directly
Pattern 2 — Command: Route AND Update State
Python · Command lets a node both update state and declare the next node
from langgraph.types import Command
from typing import Literal

def supervisor_node(state: OSDState) -> Command[Literal["sap_agent", "summary"]]:
    # Classify with LLM + update state + route in one step
    result = llm.invoke(state["messages"])
    next_node, confidence = classify(result)

    return Command(
        goto=next_node,                       # routing decision
        update={"confidence": confidence}    # state update applied BEFORE routing
    )
# With Command: no add_conditional_edges() call needed — the node declares its own routing
Pattern 3 — Send: Parallel Fan-Out
Python · Dispatch multiple agents simultaneously with per-agent state
from langgraph.types import Send

def fanout_router(state: OSDState) -> list[Send]:
    # Fan out to ALL sub-agents in parallel with individual state
    claim_id = state["claim_id"]
    return [
        Send("sap_agent",       {"claim_id": claim_id, "query": "order_status"}),
        Send("warehouse_agent", {"claim_id": claim_id, "query": "inventory"}),
        Send("fedex_agent",     {"claim_id": claim_id, "query": "tracking"}),
    ]

builder.add_conditional_edges("supervisor", fanout_router)
# All three agents run in parallel; their sub_results accumulate via operator.add
Unmapped Return Value = Runtime ErrorIf your routing function returns a string not in the path_map, LangGraph raises a ValueError at runtime (not compile time). Always include a fallback key, or use the Literal type hint on the routing function return type to catch mismatches in your IDE.

  • When do you use add_conditional_edges vs Command for routing?
    add_conditional_edges: pure routing — the routing function only reads state and decides the next node. The routing logic is separate from the node's execution. Best when routing decision is simple and deterministic given current state. Command: when you need to update state AND route in the same step — e.g., the supervisor LLM returns both a routing decision AND a confidence score that must be stored in state before the next node runs. Command is also cleaner for self-contained node logic since routing is declared inside the node function itself.
  • How do you implement parallel fan-out — multiple agents running simultaneously?
    Use Send: the routing function returns a list of Send(node_name, state_dict) objects. Each Send dispatches to the named node with its own state snapshot. All dispatched nodes run in the same superstep (in parallel). Their outputs are merged back into the parent state via reducers — which is why the accumulating fields must use Annotated[list, operator.add]. For FFF: all 5 sub-agents run in parallel via Send; their results accumulate in sub_results via operator.add, then summary runs after all complete.
  • How do you use an LLM as the routing function itself?
    Two approaches: (1) Structured output — call model.with_structured_output(RouteDecision) where RouteDecision is a Pydantic model with a next: Literal["sap", "warehouse", "fedex"] field. The routing function returns result.next. (2) Tool binding — bind a "route_to" tool and parse the tool call arguments. Both approaches make the LLM's routing decision strongly typed and validated before it reaches the path_map. The routing function receives the model's structured output — not a free-text string that might hallucinate a node name not in the path_map.
  • What happens if the routing function returns a value not in the path_map?
    LangGraph raises a ValueError at runtime with a message like "route 'xyz' not found in path_map." It does NOT fail at compile time — the graph compiles fine. Prevention: (1) use Literal type hints on the routing function return type so IDEs flag invalid returns; (2) add a catch-all key in path_map; (3) for LLM-based routing, use structured output to constrain the model's choices to valid node names only. In production, this is one of the most common runtime bugs in LangGraph.
Memory & CheckpointingPersistence · State DurabilityPersistence
Checkpointers save graph state after every node execution. thread_id is the conversation/session key — same thread_id = same accumulated state. MemorySaver is dev-only; use SqliteSaver or PostgresSaver for production.
Dev — MemorySaver (In-Process Only)
Python · Zero-dependency in-memory checkpointer for testing
from langgraph.checkpoint.memory import MemorySaver
from langchain_core.messages import HumanMessage

memory = MemorySaver()
graph = builder.compile(checkpointer=memory)

config = {"configurable": {"thread_id": "claim-OS-2024-881"}}

# Turn 1 — runs graph; state checkpointed after each node
graph.invoke({"messages": [HumanMessage("Check order status")]}, config)

# Turn 2 — previous state loaded; add_messages reducer APPENDS new message
graph.invoke({"messages": [HumanMessage("What about the warehouse location?")]}, config)
Production — PostgresSaver
Python · Multi-process durable checkpointing
# pip install langgraph-checkpoint-postgres
from langgraph.checkpoint.postgres import PostgresSaver

DB_URI = "postgresql://user:pass@host:5432/langgraph_prod"

with PostgresSaver.from_conn_string(DB_URI) as saver:
    saver.setup()    # creates schema tables — run ONCE on first deploy (idempotent)
    graph = builder.compile(checkpointer=saver)
    config = {"configurable": {"thread_id": "claim-OS-2024-881"}}
    result = graph.invoke(initial_state, config)

from langgraph.checkpoint.sqlite import SqliteSaver
with SqliteSaver.from_conn_string("./checkpoints.db") as saver:
    graph = builder.compile(checkpointer=saver)
Inspect, Roll Back, and Update State
Python · State introspection and manual update for HITL correction
# Current state snapshot
snapshot = graph.get_state(config)
print(snapshot.values)       # full state dict
print(snapshot.next)         # which nodes will run next (empty = graph finished)

# Full checkpoint history — newest first
history = list(graph.get_state_history(config))

# Roll back: replay from a past checkpoint
old_config = history[2].config
graph.invoke(None, old_config)    # resume from that snapshot

# Manual state patch before resuming (human correction)
graph.update_state(config, {"confidence": 0.95})
graph.invoke(None, config)        # continue with corrected state

  • MemorySaver vs PostgresSaver — what breaks in production with MemorySaver?
    Three failure modes: (1) Process restart — app deploy, crash, or OOM kill wipes all in-memory state; in-flight investigations are lost. (2) Multi-process — if two workers handle two turns of the same conversation, they each have their own MemorySaver dict; neither sees the other's state, so turn 2 starts fresh. (3) Serverless — function invocations don't share process memory; every call is stateless. PostgresSaver solves all three: state is stored in the DB, shared across processes, and survives restarts.
  • What happens if you call invoke() without providing a thread_id?
    Behavior depends on LangGraph version. In most versions, an anonymous/default thread is used — but this means all calls without a thread_id share state with each other, which is almost never what you want. Best practice: always provide an explicit thread_id. Without it: interrupt() may not work reliably, get_state() returns the wrong thread's state, and multi-turn continuity is broken. Always set thread_id in config.
  • How do you roll back to a previous checkpoint and re-run from there?
    Call graph.get_state_history(config) — returns a list of StateSnapshots newest-first. Each snapshot has a .config with the checkpoint ID. Pass that old config to graph.invoke(None, old_config) — the graph loads that historical snapshot and re-executes from whatever node was next at that point. If you want to change what happens: call graph.update_state(old_config, changes) first, then invoke(None, old_config). This creates a new branch — a fork in the execution history.
  • How do you implement long-term cross-session user memory?
    Two patterns: (1) Single long-lived thread per user — thread_id = user_id. State accumulates forever; history grows unboundedly; cheaper in code. (2) Short-lived conversation threads + external memory store — each conversation gets its own thread_id (e.g., user_id + session_id). A separate DB stores user facts. At conversation start, retrieve facts and inject via update_state() or include in initial state. Pattern 2 is preferred for long-lived users — it keeps conversation threads manageable and separates concerns between "what happened in this conversation" and "what we know about this user."

Multi-Step Approval Chain

def approval_node(state: OSDState) -> dict:
    # Step 1: manager approval
    mgr = interrupt({"step": "manager", "amount": state["amount"]})
    if mgr != "approve":
        return {"approved": False}

    # Step 2: director approval required for amounts over $50K
    if state["amount"] > 50000:

    return {"approved": True}

The graph must be compiled with a checkpointer so the paused state can survive between the interrupt and the eventual resume call (which may come minutes or hours later, in a different process).

  • How does interrupt() differ from interrupt_before — when do you choose each?
    interrupt(): called inside a node function based on runtime state. You control when, whether, and what payload to surface. The return value of interrupt() is the human's response — you can branch on it. interrupt_before: set at compile time — always pauses before that node, no matter what. No payload customization, no return value from the pause. Choose interrupt() for conditional approval gates (confidence threshold, amount threshold). Choose interrupt_before for always-on review steps required by regulation or for step-through debugging during development.
  • What happens to graph state while paused at interrupt()?
    The state is saved to the checkpointer as a snapshot at the exact point of the interrupt — specifically, as a task that is pending completion. The Python process can exit. When Command(resume=value) is called later (in any process that can reach the same checkpointer DB), LangGraph loads the snapshot, injects the resume value as the return of interrupt(), and continues execution from that line. This durability is the entire reason checkpointer is required — without it, there's no place to store the paused execution context.
  • How do you handle a timeout if the human never responds?
    LangGraph has no built-in timeout. External implementation: (1) When the interrupt fires, record the thread_id + timestamp in a separate DB table or Workflow-managed state. (2) A scheduled job (cron or LangGraph Workflow task) runs every N minutes and queries for threads paused longer than the SLA window. (3) The job calls graph.invoke(Command(resume="timeout"), config) with a default decision. The routing function after the approval node handles "timeout" as a separate case (e.g., auto-reject and notify supervisor). For Optum PA: the 72-hour CMS deadline is enforced this way.
  • Can multiple roles each approve a different step in one workflow?
    Yes. Pattern: sequential interrupt() calls within one node or across multiple nodes. Each interrupt() surfaces a payload with a "role" field so the frontend/notification system knows which approver to contact. The thread sits paused in the checkpointer between each approval. The full approval chain state accumulates in the state dict (e.g., approval_chain: Annotated[list, operator.add]). Each approver's decision is appended. The final summary node can see the complete chain for audit. PostgresSaver required since approvals may span days and different process instances.
StreamingObservability · Real-Time OutputObservability
LangGraph exposes graph execution in real time via stream() and astream_events(). Four primary modes: values (full state per step), updates (delta per node), messages (token-level LLM output), custom (user-emitted events). Always use version="v2" with astream_events.
stream_mode values, updates, messages
Python · Three core stream modes compared
from langchain_core.messages import HumanMessage

config = {"configurable": {"thread_id": "1"}}
inp = {"messages": [HumanMessage("Check claim OS-2024-881")]}

# values — full state dict after each node completes
for state in graph.stream(inp, config, stream_mode="values"):
    last = state["messages"][-1]
    print(f"[STATE] {last.content[:80]}")

# updates — only the dict each node returned (the delta)
for node_name, delta in graph.stream(inp, config, stream_mode="updates"):
    print(f"[{node_name}] changed keys: {list(delta.keys())}")

# messages — token-level LLM output (typewriter effect)
for chunk, metadata in graph.stream(inp, config, stream_mode="messages"):
    if hasattr(chunk, "content") and chunk.content:
        print(chunk.content, end="", flush=True)

# Multiple modes simultaneously — yields (mode_name, data) tuples
for mode, data in graph.stream(inp, config, stream_mode=["values", "messages"]):
    if mode == "messages":
        chunk, meta = data
        print(chunk.content, end="")
    elif mode == "values":
        print(f"\n[step complete]")

  • What's the practical difference between values and updates — when do you choose each?
    values: every stream chunk is the entire state dict — use when your consumer needs the full picture at each step (e.g., rendering a full state display). Downside: if state contains large accumulated lists (all sub-agent results), each chunk is large. updates: each chunk is just the dict one node returned — use when state is large or when you only care about what changed (e.g., logging which nodes ran and what they produced). For FFF's sub-agent architecture where sub_results grows after each agent: prefer updates to avoid retransmitting the full result list 5 times.
  • When do you use astream_events vs stream?
    stream(): simpler, returns state/delta chunks tied to node boundaries. Use when you need state visibility and don't need to see inside node internals (individual tool calls, token-level LLM output). astream_events(): fine-grained — you see individual events inside each node: when each tool call starts/ends, every LLM token, custom events emitted by your code. Use when: (1) streaming tokens to a UI, (2) monitoring individual tool call latency, (3) building observability dashboards, (4) handling interrupts in an async event loop. Always async — requires await/async for.
  • How do you stream token-level output from LLMs inside subgraphs?
    Use astream_events(version="v2") on the parent graph. Events from inside subgraphs automatically appear in the parent's event stream with event["metadata"]["langgraph_node"] set to the subgraph's node name. Filter on event["event"] == "on_chat_model_stream" to get tokens regardless of nesting depth. Alternatively, pass subgraphs=True to stream() — each chunk becomes (namespace_tuple, chunk) where the namespace identifies the subgraph that emitted it. The namespace is an empty tuple for the parent graph and a tuple of subgraph names for nested subgraphs.
  • How do you combine streaming with human-in-the-loop interrupts in the same event loop?
    Stream until you detect the __interrupt__ key, then break out of the loop. Using astream_events(), the interrupt appears as an event with event["event"] == "on_chain_end" on the graph node that called interrupt(), and the snapshot's .tasks[0].interrupts will contain the interrupt payload. Practical pattern: async generator that yields tokens to the UI as they stream; when interrupt detected, yield a special sentinel to the UI (triggers approval form render); UI collects human input; backend calls graph.invoke(Command(resume=decision), config); starts a new streaming loop for the remainder of execution.
SubgraphsArchitecture · CompositionArchitecture
Compile a graph and embed it as a node in a parent graph. Enables modular, independently-testable agent teams. State schemas can be shared or different — use a bridge function to translate when schemas differ.
Define, Compile, and Embed a Subgraph
Python · Subgraph with its own schema, bridged into a parent graph
from langgraph.graph import StateGraph, END, START
from typing import TypedDict

# ── Subgraph: SAP lookup agent ──────────────────────────────
class SAPState(TypedDict):
    claim_id:         str
    sap_order_status: str
    sap_amount:       float

def sap_lookup(state: SAPState) -> dict:
    result = sap_api.get_order(state["claim_id"])
    return {"sap_order_status": result["status"], "sap_amount": result["amount"]}

sap_builder = StateGraph(SAPState)
sap_builder.add_node("lookup", sap_lookup)
sap_builder.add_edge(START, "lookup")
sap_builder.add_edge("lookup", END)
sap_subgraph = sap_builder.compile()    # compile BEFORE adding to parent

# ── Parent graph ─────────────────────────────────────────────
class ParentState(TypedDict):
    messages:   list
    claim_id:   str
    sap_result: str      # will hold the subgraph's output

# Bridge function: translate parent state ↔ subgraph state
def call_sap_agent(state: ParentState) -> dict:
    sub_result = sap_subgraph.invoke({
        "claim_id":         state["claim_id"],
        "sap_order_status": "",
        "sap_amount":       0.0,
    })
    return {"sap_result": sub_result["sap_order_status"]}

parent_builder = StateGraph(ParentState)
parent_builder.add_node("supervisor", supervisor_node)
parent_builder.add_node("sap_agent", call_sap_agent)   # bridge fn wraps subgraph
parent_builder.add_edge(START, "supervisor")

graph = parent_builder.compile()

  • When should you use a subgraph vs a plain node?
    Use a subgraph when: (1) the component has its own multi-step control flow (loops, conditionals, multiple nodes); (2) you want to test it independently with its own invoke() call; (3) the same component is reused in multiple parent graphs; (4) you need schema isolation (the component has fields the parent doesn't need to know about). Use a plain node when: the logic is a single function, there's no internal branching, and it's specific to one graph. The overhead of a subgraph (bridge function, separate compilation) is only justified by the modularity benefits.
  • How do you handle state schema mismatches between parent and subgraph?
    Write a bridge function — a plain Python function (not a subgraph) that the parent registers as a node. The function: (1) reads the fields it needs from the parent state, (2) constructs the subgraph's input state dict, (3) calls subgraph.invoke(sub_input), (4) extracts the relevant output fields from the subgraph result, (5) returns a dict updating the parent state keys. The parent never sees the subgraph's internal schema — just the fields the bridge function surfaces. This is the standard pattern when subgraph schemas are domain-specific and parent schema is aggregate.
  • How does checkpointing work when a parent graph contains subgraphs?
    The parent's checkpointer automatically namespaces subgraph checkpoints. Each subgraph step is saved with a checkpoint key like thread_id:sap_agent:0. You can see subgraph steps in get_state_history() — they appear with a namespaced config. If the parent graph is interrupted mid-subgraph, the parent checkpointer saves the subgraph's partial state too. Rolling back the parent restores the subgraph to its checkpointed state. The subgraph does NOT need its own checkpointer — it shares the parent's. If you want the subgraph to also be independently resumable (e.g., a long-running external API call subgraph), give it its own compile(checkpointer=...) — but this is unusual.
  • Can you use a subgraph compiled with one checkpointer inside a parent with a different checkpointer?
    Yes, but the behavior is nuanced. When a compiled subgraph with its own checkpointer is embedded in a parent, the subgraph checkpoints to its own checkpointer using the same thread_id (potentially causing conflicts). The recommended pattern: compile subgraphs WITHOUT a checkpointer and let the parent's checkpointer handle everything via namespace. Only give a subgraph its own checkpointer if it needs to be independently invoked and resumed outside the parent graph — treat it as a standalone first-class graph in that case.

  • Why would FFF Enterprises choose LangGraph over CrewAI for OS&D investigation?
    Four concrete requirements drove the choice: (1) Durable state — an OS&D investigation can span hours (investigator interrupt, API timeouts). PostgresSaver keeps the full investigation state alive across process restarts. CrewAI has no built-in persistence. (2) Structured HITL — confidence gate requires pausing mid-execution, surfacing a structured payload (sub-results, confidence score) to an investigator, and resuming with their decision. interrupt()/Command(resume=) is exact fit. (3) Parallel fan-out — all 5 sub-agents run simultaneously via Send; results accumulate via operator.add. CrewAI supports parallel tasks but with less control over state accumulation. (4) Audit trail — get_state_history() produces a complete immutable record of every step for regulatory compliance.
  • What's the status of AutoGen in 2026, and what should I know about its successor?
    AutoGen entered maintenance mode in September 2025 — v0.7.5 was the last meaningful release, explicitly documented as receiving no new features going forward. The recommended successor is Microsoft Agent Framework (MAF), which ships production-grade features AutoGen lacked: durable task state, built-in observability, governance, and HITL support. MAF is designed for Azure-first enterprise deployments. If an interviewer mentions AutoGen, acknowledge its maintenance status and note MAF as the forward path. Don't propose AutoGen for new production systems.
  • LangGraph vs managed platforms like Databricks Supervisor Agent — when do you pick each?
    LangGraph: you control the orchestration code, deploy anywhere (cloud, on-prem, serverless), maximum flexibility in routing and state schema. Requires engineering to build and maintain the orchestration layer. Databricks Supervisor Agent / AgentBricks: no-code UI, built-in Unity Catalog governance, OBO auth, MLflow 3 tracing, Teams integration — production-ready for enterprises already on Databricks. The two aren't mutually exclusive: LangGraph is the orchestration paradigm that Databricks Supervisor Agent implements under the hood. For FFF: Databricks Supervisor Agent in production for the governed, no-code deployment; LangGraph knowledge lets you understand what's happening, debug routing, and build custom sub-agents where AgentBricks doesn't fit.
  • When would you use simple LLM chains (no LangGraph) instead of a graph?
    Simple chains (or direct API calls) are the right choice when: (1) The workflow is strictly linear with no branching or loops — document classification, single-shot summarization, one-step extraction. (2) No state needs to persist across calls. (3) No HITL requirement. (4) Latency is critical and the overhead of graph compilation and state management is measurable. Rule of thumb: if you can describe the workflow as "call LLM once or twice with fixed prompts," use a chain or direct API. When you find yourself writing "if the LLM says X, do Y, otherwise loop back and try again" — reach for LangGraph. The graph becomes necessary at the first conditional branch or loop.
