Supervisor AgentAgentBricks · OrchestrationGA
No-code orchestration layer that routes user intent to sub-agents (Genie, Knowledge Assistant, UC Function Tools). The brain of FFF's OS&D agent network — 10+ days → 1–3 minutes.
UI — No-Code Setup
  1. Navigate Workspace → AI & BI → AI Agents
  2. Click Create Agent → Supervisor Agent
  3. Name the agent; select a UC catalog/schema to register it in
  4. Add sub-agents from the palette: Genie Agents, Knowledge Assistant, UC Function Tools

  6. Click Deploy — generates a serving endpoint + MLflow trace logging automatically

Medallion Layer MappingSupervisor sits above Gold layer — queries Gold Delta tables via Genie Agent (structured), Gold Volumes via Knowledge Assistant (unstructured). Bronze/Silver are upstream and invisible to the agent at query time.
  • What is OBO authentication and why does it matter for Supervisor Agent?
    On-Behalf-Of (OBO) passes the end-user's identity token — not a service principal — to all downstream tool calls. UC row-level security and column masks enforce permissions based on who is asking, not who the agent runs as. For FFF: a warehouse manager can only query their region's inventory via the Warehouse Agent; an exec sees all. Without OBO you'd replicate row-level permissions in every sub-agent separately.
  • How does the Supervisor route to the right sub-agent?
    An LLM intent classifier reads the user's message against the registered descriptions of each sub-agent. Confidence scoring determines whether to answer or return uncertainty. The descriptions you write ARE the routing logic — make them semantically distinct and specific (e.g. "Call this when user asks about SAP order status or fulfillment records" vs "Call this when user asks about drug SOP or handling procedures").
  • How do you debug a mis-routed Supervisor query?
    Inspect the MLflow 3 trace in system.agent_traces: the span tree shows the classification decision, which sub-agent was called, inputs/outputs, confidence score. Use the Review App for interactive testing. Improve routing by editing sub-agent descriptions to be more semantically distinct.
  • Supervisor Agent vs custom LangChain agent — when would you choose each?
    Supervisor Agent: managed, no-code, UC-governed natively, built-in OBO auth, MLflow tracing, Teams integration — right for enterprise governance-first deployments like pharma distribution. LangChain: more flexibility, custom orchestration logic, multi-provider LLMs, but requires manual UC integration and auth logic. SA answer: for FFF's regulated environment, Supervisor Agent reduces implementation risk and provides auditability out-of-the-box.

  • A Genie Agent gives wrong answers about shipment status. What do you investigate first?
    Column and table descriptions in Unity Catalog. Check if ambiguous columns (status codes, date fields, quantity units) have clear COMMENT text. Second: add trusted assets — pre-validated SQL for the most common questions. Third: run Genie Benchmarks on a test set and measure accuracy.   • When would you use Genie vs a direct SQL dashboard?
    Genie for ad-hoc NL exploration by non-technical users ("which drivers had the most OS&D claims in Q3?"). SQL dashboards for known, fixed KPIs with scheduled refresh. Genie is not a replacement for dashboards — it's a dynamic query layer on top of the same Gold tables that power your dashboards.
  • How does Genie handle row-level security?
    Via OBO — it inherits the authenticated user's UC permissions. Row filters defined as SQL UDFs on the Gold table apply transparently when Genie runs its generated query. The agent never sees data the user isn't authorized to see.

  • Why register tools in UC rather than defining them inline in the agent?
    UC registration gives versioning, access control (GRANT/REVOKE EXECUTE), lineage tracking, discoverability, and reuse across multiple agents. The same get_sap_order_status function can be called by the Supervisor Agent AND directly by a Workflow job AND exposed to Teams via a different agent — without duplicating code. It's the single source of truth for that integration capability.
  • How do you handle secrets in UC function tools?
    Use Databricks Secrets: dbutils.secrets.get(scope="sap-creds", key="api-token"). Never hardcode credentials in function bodies. The function's service principal (or user via OBO) must have GET permission on the secret scope. Secrets are encrypted at rest and never appear in MLflow traces or audit logs.

  • How do you promote a model from dev to prod in UC Model Registry?
    Register a new version in the prod catalog (prod.ml.osd_classifier) — models are not moved or transitioned. Your CI/CD pipeline: (1) train in dev, register in dev.ml.*, (2) run evaluation, (3) if passing, register same artifact in prod.ml.* using copy_model_version(), (4) set @champion alias on the new version. Model Serving endpoint reads @champion automatically — no restart, no URL change.
  • What does mlflow.evaluate() measure for RAG and why is faithfulness most critical for pharma?
    Faithfulness: does the answer stay within the retrieved context (no hallucinations)? Context precision: is the retrieved context relevant? Answer relevance: does the answer address the question? Context recall: was all relevant context retrieved? For pharma distribution: faithfulness is most critical — a hallucinated drug dosage, availability status, or handling procedure is a patient safety risk and potential regulatory violation.
  • What's the difference between MLflow 3 tracing and earlier versions?
    MLflow 3 introduces hierarchical span trees (not just flat run logs) — each agent call produces a tree of spans: supervisor routing, sub-agent calls, tool invocations, each with inputs/outputs and timing. Traces are stored as Delta tables in UC (system.agent_traces) making them queryable via SQL. Earlier MLflow only had flat run metrics — not suitable for debugging multi-step agent pipelines.

CREATE CATALOG IF NOT EXISTS prod;
CREATE SCHEMA IF NOT EXISTS prod.supply_chain;

-- Row-level security: SQL UDF-based row filter
CREATE FUNCTION prod.security.shipment_region_filter()
RETURNS BOOLEAN
RETURN is_account_group_member('global-ops')
    OR current_user() = region_owner;

ALTER TABLE prod.supply_chain.shipments
  SET ROW FILTER prod.security.shipment_region_filter() ON ();

-- Column mask: hide patient ID except for PHI-access group
CREATE FUNCTION prod.security.mask_patient_id(patient_id STRING)
RETURNS STRING
RETURN CASE WHEN is_account_group_member('phi-access')

ALTER TABLE prod.supply_chain.shipments

  • Hive metastore vs Unity Catalog — key differences?
    Hive metastore: workspace-level (2-level: schema.table), no cross-workspace governance, no row-level security, no column masking, no lineage. UC: account-level (3-level: catalog.schema.table), shared across workspaces, ABAC with row filters and column masks as SQL UDFs, automatic column-level lineage, governs models, functions, volumes, and agents too. For FFF with multiple workspaces: UC is the only option for unified governance.
  • How many metastores can you have per cloud region?
    One metastore per region per Databricks account. Common exam question. Multiple catalogs within one metastore is fine, but not multiple metastores in the same region. Multi-region deployments get one metastore each; use Delta Sharing for cross-region data access.
  • Why does column-level lineage matter for pharma compliance?

  • How does Delta Lake achieve ACID without a traditional lock manager?
    Optimistic concurrency control via the transaction log (_delta_log/). Each write appends a new JSON commit entry. On conflict (two concurrent writers), the second writer checks if the first's changes overlap with its read set. No overlap (different partitions) → both commits succeed. Overlap → one is rejected and must retry. This is optimistic — assumes conflicts are rare, true for typical Lakehouse workloads where writers are partition-separated.
  • Z-ORDER vs Liquid Clustering — when do you choose each?
    Z-ORDER: stable, works on all Databricks versions, requires OPTIMIZE after significant loads, columns fixed at creation. Liquid Clustering (2024+): auto-managed, no explicit OPTIMIZE needed, change clustering columns without a full rewrite. SA recommendation: prefer Liquid Clustering for new tables on current runtime; Z-ORDER for legacy tables or compatibility requirements.

  • What is Reciprocal Rank Fusion and why does it work for hybrid search?
    RRF merges two ranked lists (BM25 results + ANN results) using: score = sum(1/(k + rank_i)) for each list, k=60 default. A document ranked high in both lists scores highest. RRF works because it's rank-based, not score-based — it doesn't require calibrating absolute similarity scores from two different metrics. Result: a document that's #1 BM25 match AND #3 ANN match scores higher than one that's #1 in only one list.
  • Delta Sync vs Direct Vector Access — when do you use each?
    Delta Sync: your source data is in a Delta table — Databricks handles embedding generation and index updates automatically via CDF. This is 90% of cases. Direct Vector Access: you compute embeddings yourself (proprietary model, pre-computed elsewhere) and push vectors directly to the index. Use when embedding generation must happen outside Databricks or you need exact control over the chunking and embedding pipeline.

  • What is the difference between data drift and prediction drift?
    Data drift: the distribution of input features changes (e.g. FedEx shipping patterns shift after a carrier partnership change — delivery times cluster differently). Prediction drift: the model's output distribution changes (more shipments flagged as OS&D risk). You need both: data drift tells you WHY model behavior may change; prediction drift tells you the model IS changing. For pharma: prediction drift could mean real-world OS&D rates are genuinely increasing OR the model is degrading — both require investigation.
  • How do Lakehouse Monitoring metrics connect to model retraining?

Serving endpoint reads @champion — no restart needed. This is the full MLOps loop, entirely within Databricks.

  • A production job that took 20 minutes now takes 4 hours. Walk me through your diagnosis.
    First: check if the data volume changed — DESCRIBE HISTORY to see if recent writes added 10× more rows than usual. Second: Spark UI → Stages → look for a stage with one task taking most of the time (data skew) or tasks with Spill columns non-zero (shuffle spill). Third: check if a new join was added recently — SortMergeJoin on a large table where BroadcastHashJoin was expected. Fourth: check for small files in source tables — DESCRIBE DETAIL to see numFiles vs previous runs. Fifth: check if AQE is enabled (spark.sql.adaptive.enabled). In practice, data skew and shuffle spill are the most common causes of sudden dramatic slowdowns on existing pipelines — they often hide until data volume crosses a threshold.
  • Why does Photon not accelerate Python UDFs, and what's the right migration path?
    Photon is a C++ vectorized query engine that operates on columnar data in JVM memory. Python UDFs require serializing each row from JVM to Python (via Py4J), running the Python function, and deserializing the result back to JVM — a row-by-row serialization loop that bypasses Photon's columnar execution entirely. Migration path: (1) check if a pyspark.sql.functions built-in covers the logic — it usually does (regex_extract, transform, array_contains, date_diff, etc.); (2) if not, write a Pandas UDF — Arrow serializes whole column batches rather than row-by-row, compatible with Photon pipelines; (3) only fall back to Python UDF for truly one-off transformations where performance isn't critical.
  • What is the minimum VACUUM retention period and why can't you go below it?
    168 hours (7 days). Going below this causes an error by default — Databricks explicitly blocks it. The reason: Delta time travel queries that reference versions within the last 7 days would return incorrect results if the underlying files were deleted. If you need shorter retention (e.g., GDPR right-to-erasure scenarios where you want old data gone faster), you must explicitly set spark.databricks.delta.retentionDurationCheck.enabled = false — which is a deliberate unsafe override, not a default. Exam: 168 hours is a commonly tested exact number.
  • When does AQE handle data skew automatically, and when does it not?
    AQE handles skew automatically for: sort-merge joins and shuffle hash joins in batch queries. It does NOT handle: streaming queries (AQE/AOS is not applied to stateful streaming), skew in the build side of a broadcast join (the broadcast happens before AQE can observe the skew), or skew in aggregation groups (only joins). For cases AQE can't handle: filter or pre-aggregate the skewed key before the join, broadcast the small side, or salt the skewed key (append a random bucket number 0–N, cross-join the small side to replicate it N times).

  • Streaming Table vs Materialized View — what's the difference and when does the wrong choice break things?
    Streaming Table (@dp.table): processes only new records since the last checkpoint — incremental. State maintained across runs. Correct for Bronze ingestion and row-level Silver transforms. Materialized View (@dp.materialized_view): fully recomputed from scratch on every pipeline run. No incremental state. Correct for Gold aggregations (SUM, COUNT, GROUP BY across all history). Common production bug: @dp.table for a GROUP BY — aggregates only the new micro-batch, so the output is always a partial aggregate, not the true historical total. Symptoms: Gold number keeps resetting rather than accumulating.
  • What are the three expectation enforcement modes and what happens to the record AND the pipeline in each?
    @dp.expect (warn): bad record KEPT, logged to pipeline_metrics, pipeline continues. @dp.expect_or_drop: bad record DROPPED, count logged to pipeline_metrics, pipeline continues. @dp.expect_or_fail: pipeline STOPS immediately on any violation — the bad record is not processed. The most important thing interviewers test: the drop and fail modes both log to pipeline_metrics, but only fail stops the pipeline. Monitor pipeline_metrics in production — expect_or_drop failures are silent to downstream consumers.
  • When do you use APPLY CHANGES vs a MERGE inside a table function?
    APPLY CHANGES is purpose-built for CDC: handles out-of-order events via sequence_by deduplication, deletes via apply_as_deletes, SCD Type 2 history automatically. A manual MERGE inside @dp.table requires custom dedup logic and doesn't handle late-arriving events (two events for the same key arriving in wrong order both get applied — the earlier one overwrites the later). For SAP or Salesforce change feeds: always APPLY CHANGES. Also creates the target table automatically.
  • Lakeflow Pipelines vs Databricks Workflows — when do you choose each?
    Lakeflow: declarative data transformation — define WHAT tables look like; Databricks handles dependency ordering, retry, data quality enforcement. Best for Bronze-Silver-Gold pipelines. Workflows: imperative task orchestration — you define the explicit task DAG (DLT pipeline + training job + model registration + serving endpoint update + Slack notification). In practice: Workflows often CALL a Lakeflow pipeline as one task inside a larger ML pipeline. You need both.

  • How does Auto Loader guarantee exactly-once ingestion?
    RocksDB checkpoint tracks every file that has been discovered and processed. On restart, Auto Loader reads the checkpoint and skips already-processed files. Combined with Delta Lake's ACID semantics (atomic writes), this gives exactly-once end-to-end. If you delete the checkpoint, Auto Loader reprocesses all files from scratch — this is the recovery mechanism, not a bug. Always back up checkpoint locations; never apply lifecycle policies to them.
  • What happens when Auto Loader hits a new column in addNewColumns mode?
    Stream stops with UnknownFieldException. Auto Loader then: (1) infers schema from the latest micro-batch, (2) merges new column to end of schema in schemaLocation. On restart (automatic in a Databricks Job), stream resumes with updated schema. Records that triggered the stop are NOT lost — they're reprocessed with the new schema. addNewColumnsWithTypeWidening additionally handles compatible type promotions (int→long) without stopping the stream at all.
  • Auto Loader standalone vs inside a Lakeflow Pipeline — which do you choose?
    Inside Lakeflow (@dp.table): preferred for new pipelines — DLT manages checkpointing automatically, expectations add data quality enforcement, UC registration is automatic, lineage is tracked. Standalone: when you need full control over streaming config (custom trigger intervals, complex multi-source fan-in, sink is not a UC Delta table) or when the rest of the pipeline isn't DLT. In practice: if you're building medallion architecture, use Lakeflow + Auto Loader together.
  • What is _rescued_data and why does it matter for production pipelines?
    When schemaEvolutionMode=none and Auto Loader receives a field not in the schema, that field is captured as a JSON string in a special _rescued_data column — never silently dropped. This is critical for auditability: even if today's schema doesn't have a new vendor field, you can query _rescued_data later and backfill when you're ready to handle it. SA recommendation: always monitor _rescued_data volume in production — a sudden increase signals source schema drift that needs investigation before it corrupts downstream tables.

  • What problem does Feature Store solve that ad-hoc feature computation doesn't?
    Three problems: (1) Training/serving skew — without Feature Store, training computes features one way and serving computes them differently; Feature Store ensures both use the same registered computation. (2) Duplicate computation — five teams computing "days since last purchase" five different ways with subtle differences; Feature Store makes features discoverable and reusable. (3) Lineage — you can't tell which models depend on which feature logic; Feature Store tracks it automatically in UC. When a feature computation changes, you know every impacted model.
  • What is a point-in-time join and why does it matter for training?
    When building a training set from historical labels (e.g., "employee X opted out on 2024-11-01"), you must use features as they existed on that date — not current values. Without timestamp_lookup_key, you'd join current feature values to past labels, accidentally giving the model "future" information it wouldn't have had at prediction time (data leakage). With timestamp_lookup_key, create_training_set joins features as-of the label_timestamp. Critical for any temporal ML problem: churn, fraud, attrition, forecasting.
  • When do you need an Online Store vs just reading from the offline Delta table?
    Online Store: when feature retrieval is on the critical path of a real-time prediction (user-facing, sub-100ms SLA). The Lakebase Online Store returns features in 5–20ms. Reading a Delta table at inference time takes 2–5 seconds minimum. If your model endpoint receives live requests and needs current features instantly (fraud scoring on a live transaction, real-time recommendation), you need Online Store. If your inference is batch (overnight scoring, daily report), offline Delta is sufficient and cheaper.
