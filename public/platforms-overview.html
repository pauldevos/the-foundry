Databricks AI PlatformModel Serving · AI Search · Genie Agents · Unity Catalog

Python · Databricks Model Serving endpoint + AI Search in a RAG chain
from databricks_langchain import ChatDatabricks, DatabricksVectorSearch
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser
import mlflow

mlflow.langchain.autolog()  # traces every chain call → system.agent_traces

# Model Serving endpoint (Foundation Model API or custom)
llm = ChatDatabricks(
    endpoint="databricks-claude-sonnet-4-5",  # or your custom endpoint
    max_tokens=512,
)

# AI Search (Unity Catalog vector index)
vectorstore = DatabricksVectorSearch(
    endpoint="hr-rag-endpoint",
    index_name="main.hr.benefit_docs_index",
    text_column="chunk_text",
    columns=["chunk_text", "source_doc", "doc_year"],
)
retriever = vectorstore.as_retriever(
    search_kwargs={"k": 5, "filters": {"doc_year": {"$gte": 2025}}}
)

rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt_template
    | llm
    | StrOutputParser()
)
answer = rag_chain.invoke("What is the 2026 PPO deductible?")
  • Why would you use Databricks AI Search over Pinecone or Qdrant?
    Three reasons that matter in enterprise. First, governance: AI Search indexes live in Unity Catalog alongside your Delta tables — the same access controls, lineage, and audit logging apply to both. No separate credentials, no shadow data. Second, Delta Sync: when your source documents table is updated (new drug labels ingested, benefits documents refreshed), the vector index syncs automatically — no separate ingestion job to maintain. Third, if you're already on Databricks for the rest of the stack (jobs, MLflow, Model Serving), staying within the platform reduces operational surface area and egress costs. The trade-off: less flexibility than a dedicated vector DB for advanced indexing strategies, and you're locked into the Databricks pricing model.
  • What's the difference between Foundation Model API and external models in Databricks?
    Foundation Model API hosts models on Databricks' own infrastructure — DBRX, Llama, Mixtral. Your data stays within the Databricks environment; never leaves for OpenAI servers. It's governed by Unity Catalog. External Models proxy calls to third-party providers (OpenAI, Anthropic, Azure OpenAI) but route them through Databricks Model Serving, which adds UC-level audit logging, rate limiting, and a single credential store. The data still goes to the external provider — but you have governance on top. For regulated industries (pharma, healthcare), knowing that PII isn't accidentally sent to OpenAI requires either Foundation Models or a very clear data classification policy with External Models.
Framework ComparisonLangGraph · LlamaIndex · CrewAI · AutoGen
No framework does everything well. The right choice depends on whether your problem is primarily about retrieval, agent state, multi-agent coordination, or all three. Picking the wrong one creates migration pain later.

The winning combination in 2026 LlamaIndex for ingestion and retrieval (index management, hybrid search, reranking) + LangGraph for agent orchestration and state (supervisor routing, HITL, checkpointing). LlamaIndex's retriever becomes a tool inside a LangGraph node. You get best-in-class at both layers.
Python · LlamaIndex retriever as a tool inside a LangGraph agent node
from llama_index.core import VectorStoreIndex, StorageContext
from llama_index.core.tools import QueryEngineTool
from langchain_core.tools import tool
from langgraph.prebuilt import create_react_agent

# LlamaIndex handles the retrieval complexity
query_engine = VectorStoreIndex.from_documents(docs).as_query_engine(
    similarity_top_k=5,
    response_mode="compact",
)

# Wrap as a LangChain tool so LangGraph can call it
@tool
def search_hr_docs(query: str) -> str:
    """Search HR benefit documents for policy, coverage, and plan information.
    Use for questions about health plans, 401k, PTO, FMLA, and benefits."""
    response = query_engine.query(query)
    return str(response)

# LangGraph handles agent orchestration, state, HITL
from langchain_anthropic import ChatAnthropic
agent = create_react_agent(
    ChatAnthropic(model="claude-sonnet-4-5"),
    tools=[search_hr_docs],  # LlamaIndex retriever as a tool
)
  • We started with LangChain but hit a ceiling. When did you switch to LangGraph?
    The ceiling hit us when we needed two things LangChain chains can't do cleanly: branching based on runtime state (if confidence is low, route to human review; otherwise auto-resolve) and resuming after a human pause. LangChain's sequential chain gave us no way to inspect intermediate state and branch on it. We were hacking around it with nested chains and callback hacks. The switch to LangGraph was the right move — state is explicit in a TypedDict, every node reads and writes it, and conditional edges are first-class. The migration took about 2 weeks because we rewrote the orchestration layer, but the retrieval layer (tools, embeddings, vector store) stayed identical — we just wrapped each retrieval step as a node.
  • Would you choose LlamaIndex or LangGraph for a new RAG project?
    It depends on whether the system is retrieval-first or agent-first. Pure document Q&A with sophisticated retrieval (multi-index, sub-question decomposition, hybrid search across 10+ document types) — LlamaIndex. It has more retrieval abstractions out of the box. If the retrieval is straightforward but I need agent behavior (dynamic routing, multi-step reasoning, HITL, checkpointed state) — LangGraph with a simple retriever. For anything non-trivial in production I'd use both: LlamaIndex's query engine as a tool inside a LangGraph node. That's the composition pattern that avoids the ceiling on either side.
Vector Databasespgvector · Qdrant · Pinecone · Databricks AI Search · Weaviate
Vector DB selection is an architectural decision with long-term consequences — migrating means re-embedding every chunk. The right choice depends on data volume, existing infrastructure, and governance requirements.
OptionWhen to useWatch out for
pgvectorAlready on PostgreSQL; <10M vectors; simple metadata filtering; low ops overheadPerformance degrades above ~1M vectors without careful HNSW tuning; no built-in hybrid BM25
QdrantOpen-source, self-hosted or cloud; built-in payload filtering; sparse+dense hybrid nativeSmaller ecosystem than Pinecone; requires ops to self-host at scale
PineconeManaged, serverless, no ops; fast startup; strong ecosystem integrationsExpensive at scale; data leaves your VPC; limited metadata filtering logic
Databricks AI SearchAlready on Databricks; Delta Sync; UC governance required; no data egressLess indexing flexibility than dedicated DBs; tied to Databricks pricing
WeaviateBuilt-in BM25+vector hybrid; multi-modal (text + image); module ecosystemMore complex to configure than Qdrant; resource-heavy self-hosted
Decision heuristic Already on Databricks → AI Search. Already on PostgreSQL, small scale → pgvector. Need open-source, self-hosted, with hybrid search → Qdrant. Need managed, fast time-to-value, not on Databricks → Pinecone. Need multi-modal or very rich filtering → Weaviate.
  • Re-embedding cost — changing vector DB means re-embedding every chunk; at 1M chunks × $0.00002/1K tokens = ~$20, but at 100M chunks it's $2,000+ and days of compute
  • Embedding model is coupled to the index — you cannot mix embedding models in the same index; a model upgrade requires a full re-index
  • Metadata schema changes — adding a new filter field (e.g., doc_year) after initial indexing requires re-ingesting all documents to backfill the field
  • The migration we ran — moved from pgvector to Databricks AI Search when the project moved onto the Databricks stack; had to: (1) export all chunks with metadata, (2) re-embed using Databricks embedding endpoint, (3) bulk-load into AI Search, (4) validate retrieval quality on eval set before switching traffic. Total time: 3 days including validation.
War Story — pgvector HNSW tuning Hit 5M vectors on pgvector. P50 query latency was 80ms — acceptable. P99 was 2,400ms — not. Root cause: default HNSW parameters (m=16, ef_construction=64) were too conservative for the index size. Tuned to m=32, ef_construction=128, rebuilt the index. P99 dropped to 340ms. Lesson: pgvector is great, but you must tune HNSW explicitly — it doesn't auto-tune, and the defaults are built for small indexes.
  • How do you choose between a dedicated vector DB and pgvector?
    Volume and ops burden are the two axes. Below 5M vectors with an existing PostgreSQL footprint: pgvector is the right default — no new infrastructure, ACID transactions, full SQL for metadata filtering. Above 10M vectors or if query P99 starts creeping up: a dedicated vector DB is worth the ops overhead. The hidden cost of pgvector at scale is that full-table HNSW index rebuilds take the table offline; dedicated vector DBs handle this incrementally. The other factor: if you need sparse+dense hybrid natively, Qdrant or Weaviate have it built in; pgvector requires a separate BM25 search to merge manually.

Python · MLflow autolog vs manual span for custom steps
import mlflow

# Autolog — covers LangChain/LangGraph automatically
mlflow.langchain.autolog(log_inputs_outputs=True)

# Manual span — for custom steps not covered by autolog
with mlflow.start_run():
    with mlflow.start_span("retrieval", span_type="RETRIEVAL") as span:
        span.set_inputs({"query": query})
        chunks = retriever.invoke(query)
        span.set_outputs({"num_chunks": len(chunks), "top_score": chunks[0].score})

    with mlflow.start_span("generation", span_type="LLM") as span:
        span.set_inputs({"num_context_chunks": len(chunks)})
        answer = llm.invoke(build_prompt(query, chunks))
        span.set_outputs({"answer_length": len(answer.content)})

  • Why would you use Arize Phoenix instead of LangSmith?
    Two situations. First: data cannot leave the organization — clinical data, PII, proprietary formulations. LangSmith sends trace data to LangChain's cloud. Arize Phoenix runs fully self-hosted inside your network; traces never leave. Second: cost. LangSmith is usage-based and gets expensive at high trace volume; Phoenix is open-source with no per-trace cost. The trade-off: LangSmith has better UX for LangGraph traces, tighter integration with LangChain's eval dataset management, and a more polished annotation workflow. For regulated industries or cost-sensitive production workloads, Phoenix is often the right call. For development and experimentation where the data isn't sensitive, LangSmith's UX advantage is worth the cost.
Framework Lock-in & MigrationWhen to switch · Migration cost · Abstraction layers
Framework lock-in in AI systems is real — but the risk is often overstated. The expensive part isn't the framework; it's the prompts, eval sets, and ingestion pipelines. Know what's coupled before you decide to switch.
  • What's actually coupled — prompts (portable), eval sets (portable), embedding model + index (re-index required), framework-specific abstractions (rewrite required), operational runbooks (rewrite required)
  • Signal 1: abstraction ceiling — you're hacking around the framework to do something it wasn't designed for (e.g., LangChain for stateful HITL). Time to switch the agent layer.
  • Signal 2: debugging opacity — you can't see what the framework is doing internally; bugs are hard to reproduce. Time to drop down to the primitive layer.
  • Signal 3: performance ceiling — framework overhead is measurable in latency and cost. Drop the abstraction, call the API directly.
  • Migration principle — never migrate everything at once. Extract the retrieval layer first (it's the most testable), validate against your eval set, then migrate the orchestration layer. Strangle the old framework over 2-4 weeks.
The strangler fig pattern for framework migration Keep the old framework running in production. Route new features through the new framework. Validate new-framework output against eval set. When new framework matches or exceeds quality, shift traffic progressively (10% → 25% → 50% → 100%). Never do a big-bang cutover on a production AI system.
  • Step 1 — identify what's truly framework-coupled (usually: retriever wrappers, output parsers, chain composition) vs. framework-agnostic (prompts, tools, eval sets)
  • Step 2 — rewrite the retrieval layer first; validate against RAGAS eval set before touching orchestration
  • Step 3 — rewrite the orchestration layer; use feature flag to route % of traffic to new implementation
  • Step 4 — run A/B for 1 week on live traffic; compare online faithfulness scores, latency P99, escalation rate
  • Step 5 — cutover; keep old code on a branch for 2 weeks as rollback
  • What would make you switch from LangGraph to something else?
    LangGraph is well-suited for complex stateful workflows, but I'd consider switching in three scenarios. First: the team is primarily non-Python (e.g., Java/Go shop) and the Python overhead outweighs the benefits — there are thinner agent frameworks in other languages. Second: we're building something simple enough that LangGraph's graph abstraction is overhead — for a single-agent ReAct loop with 3 tools, calling the API directly is less cognitive load. Third: the Databricks stack evolves to offer a native agent orchestration layer that integrates more tightly with Unity Catalog governance and MLflow tracing — at that point the switching cost vs. integration benefit might favor moving. But for now, LangGraph + MLflow on Databricks is the combination I'd reach for first.
Model Hosting Trade-offsAPI vs self-host · Cost breakeven · Latency · Compliance
API-first is almost always the right starting point. Self-hosting pays off only at scale, under specific latency requirements, or when data residency rules out cloud APIs entirely.
FactorAPI (Anthropic/OpenAI/Databricks)Self-hosted (vLLM, Ollama, Databricks Model Serving)
Time to first tokenHours (get API key, call API)Days–weeks (provision GPU, serve model, load test)
Data residencyData leaves your networkData stays in your infrastructure
Cost at low volumeLow (pay per token)High (GPU always running even when idle)
Cost at high volumeHigh (linear with tokens)Lower (amortize fixed GPU cost over many requests)
Latency P99Variable (shared infrastructure)Predictable (dedicated GPU)
Model choiceBest frontier modelsOpen weights only (Llama, Mistral, DBRX)
Breakeven rule of thumb A single A100 GPU (~$3/hr managed, ~$1.50/hr spot) can serve Llama-3-70B at ~30 tokens/sec. At that rate, 24/7 operation costs ~$1,100/month. If your API spend exceeds that, self-hosting breaks even on compute. But add ops cost (on-call, upgrades, monitoring) and the real breakeven is typically 2-3× the compute cost, so ~$3,000-$4,000/month in API spend.
  • Start with API — ship faster, iterate faster, let the model provider handle reliability; switch to self-host when the math works
  • Databricks Model Serving as middle ground — self-host open weights models on Databricks-managed GPU; you control the model, Databricks handles infra scaling; data stays in your workspace
  • vLLM for high-throughput self-hosting — PagedAttention gives 2-4× throughput vs naive serving; continuous batching handles variable request rates; good for batch inference
  • Embedding models break even early — embedding APIs cost $0.00002/1K tokens; at 10M queries/day that's $200/day. A single GPU running nomic-embed handles this for $50/day. Embedding is often the first workload to self-host.
  • When would you recommend self-hosting a model in a regulated industry?
    Two triggers that override the cost math. First, data classification: if the queries contain PHI (protected health information), PII, or CJIS-controlled data, most cloud API providers' data processing agreements don't satisfy HIPAA BAA or equivalent requirements — self-hosting inside your compliant infrastructure is required regardless of cost. Second, air-gapped environments: some defense and government workloads can't make outbound API calls at all. In those cases, Databricks Model Serving on-premises or vLLM in a private cluster is the only path. Outside those constraints, I'd always start with the API and build the case for self-hosting from real usage data rather than projections.
