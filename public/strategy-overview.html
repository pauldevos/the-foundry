Build vs BuyCustom · Vendor · Open source · Platform
The build vs buy decision in AI is more nuanced than in traditional software because the "buy" options span a wide range: fully managed platforms, open-source frameworks, foundation model APIs, and pre-built vertical solutions. The right answer depends on your differentiation, data, and ops capacity.
  • Build when the capability IS the product — if your AI is a competitive differentiator (proprietary data + workflow), buying an off-shelf solution gives competitors the same capability
  • Buy when the capability is a commodity — document summarization, generic Q&A, sentiment analysis — these are not moats; buy or use a foundation model API
  • Open source is not free — self-hosting LLMs, vector DBs, and orchestration frameworks requires GPU ops, upgrades, security patching, and on-call. Total cost of ownership is often 3–5× the apparent cost.
  • Vendor risk in AI is real — LLM providers change pricing, deprecate models, go down, or get acquired. Build with abstractions that let you swap providers (LangChain's chat interface, LiteLLM) for non-differentiating tasks.
  • Platform bet vs. best-of-breed — Databricks full-stack (Delta + UC + Model Serving + AI Search + MLflow) vs. stitching best-of-breed tools. Platform: less ops, more lock-in. Best-of-breed: more flexibility, more integration work.
Director Answer Framework "I default to buying or using APIs for anything that's not proprietary — generic NLP tasks, standard RAG retrieval, evaluation metrics. I build custom for: (1) proprietary data pipelines where we have unique signal, (2) workflows where the business logic is a competitive advantage, (3) anything requiring integration with internal systems the vendor can't support. The question I always ask: if a competitor bought the same vendor solution, would they have the same capability? If yes, it's not a moat — buy it and spend engineering time on what actually differentiates us."

  • A business unit wants to buy a vertical AI solution. What questions do you ask before approving?
    Six questions. (1) Data: where does our data go? Who trains on it? Can we opt out of training data use? (2) Integration: how does it connect to our existing systems — API, connector, manual export? What's the integration maintenance burden? (3) Customization ceiling: when our requirements outgrow the product, what's the migration path? Have they seen customers need it before? (4) Vendor viability: what's their funding situation, customer base, enterprise contract terms? AI vendor landscape is volatile. (5) Governance: does it meet our compliance requirements (HIPAA BAA, SOC 2, data residency)? (6) True cost: what's the total cost including implementation, training, support, and the overage pricing when usage scales? The sticker price is almost never the real price.
RAG vs Fine-tune vs PromptingDecision framework · When each wins · Combining
These are not competing approaches — they solve different problems. The mistake is reaching for fine-tuning before exhausting prompting and RAG, which are faster, cheaper, and more maintainable for most use cases.
ProblemBest approachWhy
Model doesn't know recent or proprietary factsRAGFine-tuning bakes in a knowledge snapshot; RAG stays current as docs update
Model uses wrong tone/format/terminologyPrompting (few-shot)Behavior is in-context learnable; 5–20 examples usually fix it
Model needs to reliably produce a specific output structurePrompting + PydanticStructured output + validation catches format errors; no training data needed
Model underperforms on a narrow, high-volume task despite good promptsFine-tuning (LoRA)Parametric knowledge injection for domain-specific patterns that prompting can't fix
Model needs domain vocabulary/jargon to score well on embeddingsFine-tune the embedding modelRetrieval domain mismatch requires embedding adaptation, not generation fine-tuning
Model knows the domain but answers from wrong docsFix RAG retrievalThis is a retrieval problem, not a model capability problem
Common Mistake — Fine-tuning the Wrong Thing Team spent 3 weeks fine-tuning a generation model because "it doesn't know our product well enough." The real problem: retrieval was returning wrong chunks. The model was hallucinating because it had no relevant context, not because it lacked product knowledge. After fixing the chunking and adding hybrid search, the base model performed fine. Three weeks of fine-tuning work abandoned. Diagnose retrieval before tuning generation.
  • RAG + prompting = solve 80% of cases — get to production faster, iterate on real user feedback, then invest in fine-tuning for the specific gaps that remain
  • RAG + fine-tuned embedding — fine-tune the embedding model on domain Q&A pairs to improve retrieval, keep the generation model as-is; often 2× improvement in context recall
  • Fine-tuned generation + RAG — fine-tune for tone, format, and domain terminology; RAG provides current knowledge; the combination is stronger than either alone
  • Prompt caching + long context instead of RAG — for small, static document sets (<100K tokens) that rarely change, long context + prompt caching can be simpler than a full RAG pipeline; no index maintenance, simpler architecture
  • When should you fine-tune instead of using RAG?
    Four situations where fine-tuning wins. First: the knowledge is stable and doesn't change — safety regulations, established medical protocols, legal statutes. RAG adds retrieval cost and latency for knowledge that could be baked in. Second: you need the model to internalize reasoning patterns, not just facts — how to analyze a contract clause, how to structure a clinical note. Retrieval can provide examples, but fine-tuning internalizes the reasoning style. Third: latency is critical — a fine-tuned small model can match a larger model on a narrow task at 10× lower latency. Fourth: you need to reduce context window usage — a fine-tuned model knows the domain implicitly, so your RAG context can be shorter. In practice, I'd almost always ship RAG first, then fine-tune for the gaps it can't cover rather than fine-tuning upfront.
POC to ProductionThe gap · Maturity model · What breaks at scale
The gap between a working demo and a production AI system is where most projects fail. A POC that impresses in a demo can take 6–12 months to harden for production. Understanding the gap before you start is what makes timelines realistic.
What works in POCWhat breaks in productionFix required
Hand-selected "good" documentsReal corpus has bad PDFs, stale docs, mixed layoutsProduction ingestion pipeline with quality gates
Manually crafted test queriesReal users ask unexpected, messy questionsReal query eval set; online monitoring
Single user, no concurrencyRate limits hit; P99 latency spikes; cost scales linearlyCaching, queuing, autoscaling, cost tracking
No access controlUsers see each other's data; confidential docs retrievedRBAC at retrieval layer; audit logging
No error handlingAPI timeouts, bad parses, model refusals crash the systemGraceful degradation, fallbacks, retry logic
Eval = "it looked good"Quality degrades silently after prompt or doc changesAutomated eval suite; regression gate; online monitoring
The Hardest Gap The hardest part of POC-to-production isn't the ML — it's the data pipeline. In the POC, someone curated 20 clean documents. In production, you need to ingest 500 documents from 12 different sources, with ongoing updates, format variations, and quality issues, on a schedule, with alerting when something goes wrong. That's a data engineering project, not an AI project. Budget for it accordingly.

  • The demo worked great, but the team is saying 6 months to production. Why so long?
    The demo showed the ML works — which is actually the easy part. What takes 6 months is: building the production data ingestion pipeline with quality validation and scheduling (4–8 weeks); building and populating the eval suite with real user queries and domain-expert-validated answers (2–4 weeks); implementing access control, audit logging, and compliance requirements (3–6 weeks depending on regulatory burden); building the monitoring infrastructure and runbooks (2–4 weeks); load testing, fixing the P99 latency issues that don't show up in single-user demos (2–4 weeks); deployment pipeline with staging environment, eval gates, and rollback procedures (2–4 weeks). None of this is glamorous, but all of it is necessary. The demo proves feasibility; the 6 months is the production engineering. If leadership is surprised by this, it means the POC was presented as a production system — which is a communications problem worth fixing before the next project.
When to Use AgentsChain vs agent · Complexity threshold · Cost of autonomy
Agents are powerful and overused. Every agentic step adds latency, cost, and unpredictability. The right question isn't "could an agent do this?" but "does this problem require dynamic, runtime decision-making that a fixed pipeline can't provide?"
Use a chain/pipeline whenUse an agent when
Steps are known and fixed at design timeSteps depend on what the system discovers at runtime
Every query follows the same pathDifferent queries need different tools or sequences
Latency and cost matter and must be predictableFlexibility and task completion matter more than predictability
The task is well-defined and boundedThe task is open-ended or exploratory
You need 100% reproducibility for auditThe plan-and-execute pattern provides the audit trail
  • Agents are not always better — a 3-step chain that reliably does the right thing beats an agent that sometimes loops, sometimes uses the wrong tool, and costs 5× more per query
  • Start with the simplest architecture that could work — chain first; add dynamic routing only when the chain demonstrably can't handle the variance you observe in production
  • Cost of autonomy — every decision the agent makes instead of deterministic code is a source of variance; for high-stakes decisions (financial, medical, legal), prefer explicit logic over agent judgment
  • The hardest agent problems are coordination — multi-agent systems add inter-agent communication, shared state management, and cascade failure risks; worth it only when a single agent genuinely can't do the job
  • Signal 1: branching based on content — "if the document is a contract, do X; if it's a spec, do Y" — you can't determine which at design time without seeing the document → agent
  • Signal 2: unknown number of steps — "investigate this issue until you find the root cause" — you don't know upfront how many tool calls it takes → agent
  • Signal 3: tool selection depends on prior results — "search the web if the internal docs don't have the answer" — the decision to use the second tool depends on the first result → agent
  • Non-signal: "it's complex" — complexity alone doesn't justify an agent; a very complex but fixed pipeline is still a chain. If you can enumerate all the paths, it's a chain with conditionals.
  • Non-signal: "we want it to be smart" — intelligence comes from the model, not from the agent architecture. A well-prompted single LLM call is often smarter than a poorly-designed agent loop.
  • How do you decide between a RAG chain and a RAG agent?
    One question: does every query follow the same retrieval path, or does the retrieval strategy depend on what the model discovers mid-query? A standard HR benefits question — "what's the PPO deductible?" — always follows: embed query → search benefit docs → generate answer. That's a chain. The retrieval strategy is fixed. An agent is warranted when: the query might require checking multiple indices (benefits docs + plan comparison + enrollment calendar) and which indices to check depends on what the query is about; or when the answer to the first retrieval changes what to retrieve next ("the PPO doesn't cover this — is it covered under the supplemental plan?"). If fewer than 20% of your queries need dynamic retrieval, serve all of them with a chain. The 20% that need it will just get the chain path, which is acceptable.
Org Buy-in & ROIStakeholder mapping · Metrics · Pilot design · Failure modes
The best AI system fails if the organization doesn't trust it, adopt it, or fund its operation. Getting buy-in is as important as building the system — and requires a different skill set than engineering.
  • Find the champion first — one VP or Director who feels the pain the AI solves is worth more than 10 technical supporters; they provide budget, air cover, and access to real data
  • Show, don't tell — a 30-minute demo on real company data beats a 30-slide deck; executives need to see it work on their problem, not a generic example
  • Address the fear directly — "will this replace my team?" is always in the room; address it early: "this handles the low-value repetitive work; your team focuses on judgment calls and exceptions"
  • Design the pilot for a visible win — pick the use case with: (a) a measurable before/after, (b) a champion who will broadcast the result, (c) low regulatory risk for the first version
  • Measure what the business cares about — not RAGAS scores; hours saved per week, resolution time, error rate, cost per transaction, employee satisfaction. RAGAS is for you; the business metric is for them.
The Pilot Design Rule A pilot that succeeds quietly fails organizationally. Design the pilot so the result is visible to leadership, the champion can point to a number, and the failure mode (if it happens) is contained and recoverable. A pilot that half the company hears about succeeding funds the next project. A pilot that no one hears about — even if technically successful — doesn't.

  • Leadership is skeptical after a failed AI project. How do you rebuild confidence?
    Don't pitch technology — pitch a contained, measurable problem. The failed project probably over-promised and under-delivered on scope. Rebuild trust with a small win: "I want to solve one specific, painful problem for one team in 6 weeks, with clear success metrics defined upfront. If it doesn't hit the metrics, we stop." Pick the problem with the most sympathetic champion and the clearest measurement. Build a paper trail: define the metrics before you start, measure them weekly, report honestly including setbacks. When you deliver — even something modest — the champion broadcasts it. That social proof is worth more than any technical argument. Then use that success to scope the next project, slightly larger. Trust is rebuilt incrementally, not in a single pitch.
AI Technical DebtPrompt debt · Eval debt · Model lock-in · Data debt
AI systems accumulate technical debt faster than traditional software, and it's less visible. A prompt that "just works" with no tests, an eval set that was never updated, a model version no one wants to upgrade — these are AI debt, and they compound.
Debt typeWhat it looks likeCost of ignoring
Prompt debtSystem prompts with no version history, no tests, modified by hand in productionSilent regressions; can't roll back; no one knows what changed or when
Eval debtEval set built once at launch, never updated with real user queries or new failure modesFalse confidence; system degrades on real traffic while eval scores stay green
Model lock-in debtPrompts so model-specific they break on any version upgrade; no abstraction layerStuck on deprecated model version; expensive migration when provider forces upgrade
Data pipeline debtIngestion script that works but has no tests, no monitoring, no quality gateBad docs silently corrupt the index; discovered when users complain, not when docs change
Observability debtNo tracing, no quality metrics, no cost tracking — "it seems to be working"Can't debug production failures; can't prove value to stakeholders; cost surprises
The Hardest Debt to Pay Down Eval debt is the most insidious. An outdated eval set gives you false confidence. You ship changes that look good on the eval but degrade on real traffic. Users complain; you can't diagnose it because your eval doesn't represent real queries. Paying it down requires going back to real user logs, having domain experts re-validate answers, and rebuilding the eval set — while the system is in production and users are depending on it. Prevention: allocate 10% of AI engineering time to eval maintenance, not as a one-time project but as ongoing operational work.
  • Treat prompts like code — version control, code review, tests, and deployment pipelines for system prompt changes; no hand-editing production prompts
  • Eval set maintenance as a quarterly ritual — review the eval set every quarter; add the top 10 failure cases from the prior quarter; remove examples that no longer represent real queries
  • Abstraction layer over model APIs — use LiteLLM or LangChain's chat interface so swapping providers is a config change, not a code rewrite
  • Data pipeline SLA — treat the ingestion pipeline as a production service with an SLA; alert on parse quality drops, staleness, and indexing failures like you would a web service outage
  • Debt inventory — maintain a visible list of known AI debt items with an owner and a target date; make it part of sprint planning, not a separate backlog that never gets touched
  • Your AI system has been running for a year with minimal engineering attention. How do you assess its health?
    Five-point health check. (1) Model currency: is the model version still supported? Are we on an alias that may have silently updated? Run the eval suite on the current pinned version vs. the latest available. (2) Eval validity: pull the 50 most recent user queries from the logs. How many are represented in the eval set? If <30%, the eval set is stale — it's measuring old behavior, not current usage. (3) Data freshness: when was the document corpus last updated? Are there stale docs in the index? What's the parse quality distribution? (4) Cost trajectory: is cost per query trending up? Often means prompts have gotten longer, agents are looping more, or the model was quietly upgraded to a larger tier. (5) User signal: what's the thumbs-down rate? Escalation rate? Support ticket volume for AI-related issues? These lagging indicators tell you what the automated metrics missed. After this assessment, I'd know what to fix and in what order.
