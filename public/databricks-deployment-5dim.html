Deployment and CI/CD for Databricks Apps

Declarative Automation Bundles (formerly Databricks Asset Bundles) are the project boundary: source, resource definitions, targets, permissions and tests travel together. GitHub Actions provides the change-control plane; Databricks owns the workspace resource lifecycle.

The five questionsBundles + workload identity federation
The critical App-specific detail: bundle deploy updates source/resources but does not necessarily restart the running app; run the app resource and poll health.
What Bundles own
LayerBundle concern
SourcePython/Node app, notebooks, wheels, SQL, tests, config.
ResourcesApps, jobs, pipelines, serving endpoints, dashboards, schemas, volumes and permissions.
TargetsDev/staging/prod workspace host, root path, variables, mode and run-as identity.
LifecycleValidate → plan → deploy → run/restart → poll health → promote/rollback.
One repositoryKeep app code and databricks.yml together. The pull request should show both behavioral code changes and infrastructure/permission changes.
Use / don't use
Use Bundles when…Use another mechanism when…
Multiple environments, code review, repeatable deployment, app resources, jobs or pipelines.You are doing a one-off UI experiment in Free Edition; still graduate the artifact into a bundle before production.
GitHub Actions must validate and deploy without long-lived secrets.The organization mandates Terraform for account-level/network resources; use Terraform where it owns infra and Bundles for workspace project assets.
You need target-specific variables and promotion gates.You need a full container release platform, cross-cloud deployment graph, or non-Databricks runtime orchestration.
Promotion invariantBuild once, promote the same commit. Do not “fix” production through the UI without recording the equivalent bundle change.
GUI build and inspect
  1. Create the app and resources in the workspace UI to discover the correct resource types, permission verbs and environment variables.
  2. Use Sync files or the Databricks VS Code extension to export the app source; inspect generated paths and runtime settings.
  3. Use the app overview to validate resource permissions, logs, deployment status, URL and restart behavior.
  4. Use Git folders for branch review, but treat the bundle as the authoritative deployable definition.
  5. For manual recovery, bind an existing app to the bundle: databricks bundle deployment bind app_key app-name --target prod --auto-approve.
GUI is discovery; code is controlThe UI is valuable for learning the service and diagnosing logs. It is not a substitute for source-controlled app resource definitions, identity grants and target variables.
GitHub Actions skeleton
name: Deploy Databricks App
on: {workflow_dispatch: {}}
permissions: {id-token: write, contents: read}
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: prod
    env:
      DATABRICKS_AUTH_TYPE: github-oidc
      DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}
      DATABRICKS_CLIENT_ID: ${{ vars.DATABRICKS_CLIENT_ID }}
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle validate --target prod
      - run: databricks bundle plan --target prod
      - run: databricks bundle deploy --target prod
      - run: databricks bundle run evidence_app --target prod
      - name: Wait for app health
        run: |
          for i in $(seq 1 20); do
            state=$(databricks apps get evidence-app --output json | jq -r '.app_status.state')
            echo "attempt $i: $state"
            [ "$state" = RUNNING ] && exit 0
            sleep 15
          done
          exit 1
Required gates

PR

Lint, type-check, unit tests, bundle validate, security scan, golden retrieval/eval tests.

Staging

Deploy, restart, health poll, smoke API, permissions/OBO test, latency and cost budget.

Prod

Protected environment reviewer, OIDC federation, immutable commit, audit record and rollback artifact.

Rollback

Redeploy prior known-good commit; do not rely on a UI restart to restore old source.

Limits, alternatives, security, cost
ConcernDecision
OIDCPrefer GitHub workload identity federation and short-lived tokens over stored PATs/client secrets. Restrict repository, branch, environment and SP permissions.
TerraformUse for account/workspace/network primitives when required; use Bundles for application resources and code. Avoid two tools owning the same object.
Deploy ≠ restartAlways run the app resource after deploy and poll RUNNING; startup failures otherwise look like successful CI.
DriftDetect UI/manual changes with plan and review. Bind existing apps instead of recreating them with duplicate names.
CostCI runners, app compute, SQL/serving endpoints and test data all contribute. Add smoke tests and auto-stop/scale policies where supported.
Free EditionUse the same bundle shape locally, but expect missing enterprise federation, quotas, previews, private network controls and scale. Do not infer production limits from Free.
