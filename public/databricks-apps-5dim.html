Databricks Apps

Serverless, workspace-native applications for governed data and AI. Treat an app as a product boundary: app service principal, optional user/OBO authorization, declared Databricks resources, a small stateless web runtime, and a separately governed data/AI plane.

Mental model
PlaneWhat belongs thereArchitectural consequence
App runtimePython/Node process, UI, API routes, short-lived request stateKeep it stateless; put durable state in Delta/Lakebase/another declared resource.
App identityDedicated app service principalEvery resource grant is explicit and auditable; never paste a PAT into app code.
Databricks resourcesSQL warehouse, serving endpoint, Genie agent, secret, volume, job, another appDeclare a resource key and let the platform inject connection details/credentials.
User identityWorkspace SSO plus optional user authorization/OBO scopesChoose app-wide permissions for service workflows; OBO when row-level permissions must follow the user.
Best fitInternal data products, RAG chat, evidence review, operational forms, model-explanation tools, and thin front ends over governed Databricks services. Apps are not a general-purpose Kubernetes replacement.
Use / don't use
Use Apps when…Prefer another boundary when…
Users already live in a Databricks workspace and data access is governed by Unity Catalog.The audience is anonymous/public, global edge delivery matters, or SEO/static content dominates. Use a CDN/static host and call a protected API.
The app is a thin interaction layer over SQL, model serving, AI Search, jobs, or Lakebase.You need long-running workers, WebSockets at scale, GPU orchestration, custom network ingress, or a large mutable cache.
Speed and governance matter more than bespoke infrastructure.You need multi-cloud portability or a provider-neutral runtime; use a container platform and integrate Databricks via APIs.
Decision rulePut business logic and controls in UC-governed services; keep the App layer replaceable. If deleting the app would delete your only copy of state, the state is in the wrong place.
GUI sequence
  1. Workspace → New → App; choose a template (Streamlit, Dash, Gradio, React/Node) or custom app.
  2. Connect a Git folder or upload/sync source; keep app.yaml at the project root.
  3. In Resources, add the SQL warehouse, serving endpoint, Genie agent, secret, volume, job, or app dependency. Assign the least privilege and a stable resource key.
  4. Configure environment variables, compute size, permissions to view/use/manage, and optional user-authorization scopes.
  5. Deploy; inspect deployment logs, app logs, health state, and running URL. Use the built-in review/share path for workspace users.
  6. For a UI-only app use app authorization; for data that must respect the signed-in user's UC permissions, enable user authorization/OBO and request only required scopes.
GUI review checklist

Identity

Who owns the app SP? Which users can view/use/manage it? Is user authorization enabled and consent understood?

Resources

Are warehouse, endpoint, volume, secret, job and app resources explicit? Does the app SP have only the required grants?

Runtime

Is the command explicit in app.yaml? Are dependencies pinned? Are port and health behavior correct?

Operations

Where do logs, telemetry, traces, cost and audit events go? What is the restart/rollback plan?

# app.py (FastAPI sketch)
from fastapi import FastAPI
from databricks.sdk import WorkspaceClient
import os

app = FastAPI()
w = WorkspaceClient()  # uses injected app credentials in Databricks

@app.get("/api/health")
def health(): return {"ok": True}

@app.get("/api/answer")
def answer(q: str):
    # Prefer an app resource key / injected endpoint, never a hard-coded PAT.
    return {"question": q}
Bundle resource (production shape)
resources:
  apps:
    evidence_app:
      name: evidence-app
      source_code_path: ./apps/evidence
      resources:
        - name: sql
          sql_warehouse:
            id: ${var.warehouse_id}
          permission: CAN_USE
        - name: search
          serving_endpoint:
            name: evidence-search
          permission: CAN_QUERY
targets:
  prod:
    mode: production
    workspace:
      host: ${var.host}
# Deploy then explicitly restart:
# databricks bundle deploy --target prod
# databricks bundle run evidence_app --target prod
Local loopdatabricks apps run-local --prepare-environment --debug starts the app proxy at http://localhost:8001; attach VS Code's Python debugger to the debug port. This is the fastest feedback loop before a workspace deploy.
Limits and alternatives
ConcernTradeoff / mitigation
File sizeApp files cannot exceed 10 MB each; keep large PDFs/images in UC Volumes and store metadata/chunks in Delta.
Runtime shapeServerless, bounded app compute; no assumption of durable local disk or singleton process. Externalize sessions, queues, and durable state.
IdentityEach app has a dedicated SP. App authorization is stable and simple; user authorization is more precise but currently preview/consent-sensitive. Test both.
Cost/availabilityApps consume provisioned app compute while running and have workspace/region limits. Confirm Free Edition and region entitlements before promising production behavior.
PortabilityResource keys and injected auth are Databricks-native. Keep UI/API contracts clean if you may later move to containers or a CDN.
AppKit vs ReactAppKit accelerates React + Databricks data access with typed queries/components; choose plain React when you need maximum ecosystem/control. AppKit does not remove the need to understand auth, state and bundle deployment.
AlternativesStatic CDN for public/SEO content; Streamlit/Gradio for speed; custom React/Node for richer UX; external container runtime for edge, long-running, or specialized network needs.
Architecture interview line“The app is a governed interaction surface, not the data plane. I declare resources, grant the app identity least privilege, use OBO only when user-level enforcement is required, and keep durable state and retrieval artifacts outside the process.”
