Why Evals Are HardNo single right answer · Cost · Speed
Traditional software has a pass/fail test. LLM outputs have a distribution of acceptable answers. "Correct" is often context-dependent, subjective, or requires domain expertise to verify. This is the core challenge evals must solve.
  • Many valid outputs — "Summarize this policy in 2 sentences" has thousands of correct answers. You can't assert equality like a unit test.
  • Correctness requires domain knowledge — is the drug interaction answer clinically accurate? You need a pharmacist, not a string match.
  • Human eval doesn't scale — hiring annotators for every prompt change is expensive and slow. Human eval is ground truth but can only be sampled.
  • Metric-task mismatch — BLEU/ROUGE were designed for translation. They correlate poorly with human judgment on open-ended generation tasks.
  • The eval trilemma — you can have two of: fast, cheap, accurate. Human eval = accurate + cheap but slow. LLM-as-judge = fast + cheap but biased. Model-based metrics (RAGAS) = fast + accurate but costs per eval call.
The Right Mental Model Think of evals as a test pyramid: a large base of cheap automated metrics (RAGAS, string match, regex), a middle layer of LLM-as-judge on sampled outputs, and a small top of periodic human review on edge cases. Each layer catches different failure modes. None alone is sufficient.

  • How do you know if your evals are actually measuring the right thing?
    Correlation with human judgment is the only real test. Take 50-100 outputs, have domain experts score them, then compute Spearman correlation between your automated metric and the human scores. If it's above 0.7, your metric is tracking what matters. Below that, you're optimizing for the wrong thing. We ran this calibration when we first set up RAGAS — faithfulness correlated well (0.82) but answer relevancy correlated poorly (0.51) because our judge model was rating grammatical fluency, not whether the answer matched the user's intent. We replaced it with a custom rubric.
  • What's the most common eval mistake you've seen?
    Building the eval set AFTER the system, then using the same examples you already fixed to tune the system. That's overfitting disguised as evaluation. The eval set must be held out — built from real user queries before you know what your system gets wrong, and never touched during development. A second common mistake: reporting averages. A 0.85 faithfulness average with a 0.40 tail for edge cases is dangerous — the average hides the failure mode that will actually surface in production.
LLM-as-JudgeBias · Rubrics · Multi-model · Calibration
Using an LLM to evaluate LLM outputs is scalable and increasingly accurate — but it comes with systematic biases that must be designed around. The judge model is not neutral.
BiasWhat it doesMitigation
Self-consistencyModel rates outputs similar to its own generation style higherUse a different model as judge than the one generating answers
Position biasRates the first option higher in pairwise comparisonsRun comparison twice, swap order; only count agreement
Verbosity biasLonger answers rated higher even when less accurateExplicit rubric: "rate only accuracy, not length"
SycophancyIf the prompt says "this is a great answer, how would you rate it?" the judge agreesNever prime the judge; present context neutrally
Authority biasAnswers citing sources rated higher regardless of citation accuracySeparate faithfulness check: verify citations exist in retrieved context
War Story — Self-Consistency Trap Used GPT-4o to generate clinical drug interaction summaries and GPT-4o to judge them. Faithfulness scores: 0.91. Switched to Claude Sonnet as the judge — scores dropped to 0.74. Investigated: GPT-4o was rating its own verbose style highly. Claude penalized vague hedging language that GPT-4o had been generating. The real faithfulness was 0.74. We'd been shipping a system that was less accurate than we thought for 3 weeks.
Python · Structured LLM-as-judge with rubric and different model
from pydantic import BaseModel, Field
from langchain_anthropic import ChatAnthropic

class JudgeScore(BaseModel):
    reasoning: str = Field(description="Step-by-step evaluation before scoring")
    faithfulness: int = Field(ge=1, le=5, description="1=hallucinated, 5=fully grounded")
    relevance:   int = Field(ge=1, le=5, description="1=off-topic, 5=directly answers question")
    completeness:int = Field(ge=1, le=5, description="1=missing key info, 5=comprehensive")

JUDGE_PROMPT = """Evaluate the assistant's answer against the reference documents.
Score ONLY based on the rubric below. Ignore answer length and writing style.

Rubric:
- Faithfulness: Does every claim appear verbatim or as a clear inference in the documents?
- Relevance: Does the answer directly address the user's question?
- Completeness: Does the answer include all key information from the documents?

Documents: {context}
Question: {question}
Answer: {answer}"""

# Judge model is DIFFERENT from the generation model
judge = ChatAnthropic(model="claude-sonnet-4-5").with_structured_output(JudgeScore)

def evaluate_answer(question, answer, context) -> JudgeScore:
    return judge.invoke(JUDGE_PROMPT.format(
        context=context, question=question, answer=answer
    ))
  • Your LLM-as-judge scores were high but users were unhappy. What went wrong?
    Metric-task mismatch. The judge was scoring faithfulness and fluency — both were high because the answers were well-written and grounded in the documents. But users were asking procedural questions ("how do I submit a PTO request?") and getting policy descriptions ("employees are entitled to X days of PTO per year"). Technically faithful, completely unhelpful. We added a new rubric dimension: actionability. "Does the answer tell the user what to do, not just what is true?" That score was 0.48. Fixed by adding procedural examples to the prompt and adding a step-by-step output requirement for "how do I" queries.
RAGAS Deep Dive4 metrics · Diagnosis map · Failure modes
RAGAS gives you four independent signals. Each one points to a specific pipeline layer. Reading them together tells you WHERE to fix the system, not just that it's broken.
MetricFormula (simplified)Low → fix hereCommon cause
FaithfulnessClaims in answer that appear in context / total claimsGeneration layerModel ignoring context, hallucinating from parametric memory
Answer RelevancySimilarity of reverse-generated questions to original questionRetrieval + promptWrong chunks retrieved; model off-topic; incomplete answer
Context RecallGround truth statements covered by retrieved contextRetrieval (chunking, embedding, search)Wrong chunk boundaries, domain embedding mismatch, doc not in index
Context PrecisionUseful chunks / total retrieved chunksRetrieval (top-K, reranking)Top-K too large, reranker needed, BM25 returning noise
Diagnosis Decision Tree Context Recall low → fix retrieval (chunking, embeddings, hybrid search) before touching anything else. Context Precision low with Recall high → add reranker or reduce K. Faithfulness low with Recall high → fix the generation prompt (grounding, citation requirements). Answer Relevancy low with Faithfulness high → the answer is grounded but doesn't address the question — check retrieval relevance and prompt focus.
  • Always fix recall before precision — if the right chunk isn't retrieved, nothing else matters
  • Sample failing cases — aggregate metrics hide patterns; look at the 10 lowest-scoring examples per metric manually
  • Requires ground truth for recall — faithfulness and precision don't need it, recall does; this is why golden datasets matter

    )

    # Log aggregate scores
    for col in ["faithfulness", "answer_relevancy", "context_recall", "context_precision"]:
        mlflow.log_metric(col, scores[col].mean())
        mlflow.log_metric(f"{col}_p10", scores[col].quantile(0.10))  # tail matters

    # Log full results as artifact for later analysis
    scores.to_csv("eval_results.csv", index=False)
    mlflow.log_artifact("eval_results.csv")

    # Flag regressions vs. last run
    last = mlflow.search_runs(order_by=["start_time DESC"], max_results=2)
    if len(last) > 1:
        delta = scores["faithfulness"].mean() - last.iloc[1]["metrics.faithfulness"]
        if delta < -0.05:
            mlflow.set_tag("alert", f"faithfulness regression: {delta:.3f}")
  • Context recall was 0.65 and faithfulness was 0.90. What's your diagnosis?
    Good news and bad news. Good news: when retrieval does find the right content, the model uses it faithfully — generation is working. Bad news: retrieval is only finding the relevant chunk 65% of the time, which means 35% of user queries are getting answers built on incomplete or wrong context — and those answers are being generated faithfully from that incomplete context, which means they're confidently wrong. Fix retrieval first: check chunk boundaries (are the right sentences being cut?), check if the embedding model handles the domain vocabulary, add BM25 hybrid if you're not using it. Don't touch the generation layer until recall is above 0.80.
Ground Truth CreationGolden sets · Synthetic · Human labels · Slice testing
The quality of your eval is bounded by the quality of your ground truth. Bad labels produce misleading scores. Eval set construction is a product decision, not a data engineering task.
  • Sample from real queries first — build your eval set from actual user queries before you know what the system gets wrong; engineer-written test cases miss the long tail
  • Include hard negatives — questions where the answer is NOT in the documents; these catch the failure mode where the model confidently hallucinates
  • Multi-hop questions — "does the PPO plan cover the medication my doctor prescribes for my condition?" requires combining plan coverage + drug formulary + prior auth rules; single-chunk retrieval fails these
  • Domain expert validation — HR attorneys review benefits answers, pharmacists review drug data, engineers review pipeline safety specs; wrong ground truth is worse than no ground truth
  • Slice testing — break the eval set into slices by query type (factual lookup, comparison, procedural, unanswerable); aggregate score can hide that one slice is broken
Synthetic Generation Trade-off LLMs can generate Q&A pairs from your documents at low cost (RAGAS testset generator, Giskard). Fast to bootstrap — but the generated questions are biased toward what appears verbatim in the docs, not how users actually phrase queries. Use synthetic to cover breadth quickly; sample real user queries to cover the distribution that matters. Validate a random sample of synthetic pairs against domain experts before using them as ground truth.

  • How many examples do you need in a golden eval set?
    Enough to detect a 5% regression with statistical confidence — typically 100-200 examples. Below 50, you're rolling dice; variance is too high to distinguish a real regression from noise. Above 500, the cost of running evals per PR becomes prohibitive. Practical approach: start with 30-50 hand-crafted examples that cover your most important query slices. Add real user queries as they come in. Use synthetic generation to quickly expand coverage. Run the full set weekly; run a 30-example "smoke test" subset on every code change. Grow the set over time as you discover edge cases.
  • What do you do when domain experts disagree on the ground truth?
    That disagreement is data, not a problem. If two pharmacists disagree on a drug interaction answer, that query should be flagged as ambiguous and excluded from automated evals — or included with multiple valid answers and scored for partial credit. More importantly, it signals a question your system should NOT answer autonomously: it should escalate to a human. The disagreement rate among your domain experts is a ceiling on the automated eval accuracy you can achieve. If experts agree 85% of the time, your automated eval can at best approach that — and you should be skeptical of any metric claiming higher accuracy than human inter-rater agreement.
Regression & CIEval-first dev · Change detection · Prompt pinning
Prompt changes, model upgrades, and chunking tweaks all cause regressions — often on edge cases you fixed earlier. Without a regression suite, every improvement risks breaking something else.
  • Prompt changes are code changes — any edit to a system prompt, few-shot example, or output format should trigger the full eval suite, not just manual spot-checking
  • Model upgrade = unknown regression — when the LLM provider releases a new version, behavior changes in ways you didn't anticipate; run evals before switching in production
  • Regression subset — keep a slice of 15-20 queries that previously failed and were fixed; run these on every change; this is your "don't break what we fixed" gate
  • Eval-first development — when a user reports a failure, add that query to the eval set FIRST, then fix it; prevents fixing the same bug twice
  • Statistical significance — a 0.02 score change on 50 examples is noise; require a 0.05 change on 100+ examples before calling it a regression or improvement
War Story — Model Upgrade Regression Upgraded from claude-haiku to claude-sonnet thinking it was strictly better. Faithfulness went from 0.81 to 0.88 on the main eval set — looked great. Deployed. Three days later, users reported that "unanswerable" questions were getting hallucinated answers instead of "I don't have that information." The new model was more confident and less willing to decline. Our eval set had only 2 "unanswerable" examples — not enough to catch the regression. Added 20 unanswerable examples to the eval set and caught the failure before the next upgrade.
Python · Eval CI gate — block deployment if regression detected
# Run as part of CI before merging prompt or pipeline changes
import sys

THRESHOLDS = {
    "faithfulness":       0.80,
    "context_recall":     0.78,
    "answer_relevancy":   0.75,
    "context_precision":  0.70,
}
REGRESSION_TOLERANCE = 0.05  # allow up to 5% drop vs baseline

scores = run_eval_suite()          # returns dict of metric → score
baseline = load_baseline_scores()  # scores from last approved run

failures = []
for metric, threshold in THRESHOLDS.items():
    score = scores[metric]
    base  = baseline.get(metric, threshold)
    if score < threshold:
        failures.append(f"{metric} below minimum: {score:.3f} < {threshold}")
    elif score < base - REGRESSION_TOLERANCE:
        failures.append(f"{metric} regression: {score:.3f} vs baseline {base:.3f}")

if failures:
    for f in failures: print(f"FAIL: {f}")
    sys.exit(1)
print("All eval gates passed.")
  • You changed the chunking strategy and evals improved overall but something broke. How did you catch it?
    The regression subset caught it. We keep 20 queries that previously failed and were fixed — every change runs against this subset first. The chunking change improved context recall on narrative queries from 0.74 to 0.83, but the regression subset showed that 3 table-heavy queries regressed from correctly answered to incorrect. The new semantic chunker was treating table rows as natural boundaries and splitting them. The overall metric improved because we had 15x more narrative queries than table queries in the eval set. Slice metrics — looking at table queries separately from narrative queries — was what made the regression visible. Now every change reports per-slice metrics, not just aggregate.
Production MonitoringOnline evals · Drift · Human feedback · Alerts
Offline evals tell you how the system performs on your test set. Production monitoring tells you how it performs on real users, with real data, that changes over time. Both are required.
  • Online eval = sample & score in production — run automated metrics (faithfulness, relevancy) on 5-10% of live traffic; alert when scores drop below threshold
  • Distribution shift — users ask different questions than your eval set; new document types get ingested; model updates change behavior; all cause silent degradation
  • Human feedback loop — thumbs up/down, corrections, escalations are the highest-signal production data; build a pipeline to convert these into new eval examples
  • Trace every request — log query, retrieved chunks, answer, latency, and cost per request; you cannot debug production failures without this data
  • Escalation as signal — if the system is routing to human review more than baseline, something is degrading; track escalation rate as a leading indicator
MLflow Traces on Databricks MLflow 2.15+ captures agent traces automatically with mlflow.langchain.autolog(). Traces land in system.agent_traces Delta table — queryable with SQL, retained for 90 days by default. Use this for production debugging: filter by low faithfulness scores, group by query_type, find the failure pattern.

    Two signals fired before any user report. First, online faithfulness scores sampled from 10% of production traffic dropped from a 7-day rolling average of 0.83 to 0.71 over 4 days.
